## Технология и почему выбрана (ответ на Q-8.1b)

**Нативная DLL на C++ (MinGW-w64 `g++`), загружаемая в целевой процесс стандартным способом
`CreateRemoteThread` → `LoadLibraryW`.** Выбрана по прямому указанию владельца — приоритет для
первого IPP-вызова: **минимальная неопределённость корректности, а не минимальный объём
записанного**. Рассмотренная и отклонённая альтернатива — shellcode-стаб (голые байты машинного
кода вместо скомпилированного C++): даёт меньший footprint, но каждая правка требует ручной
пересборки байт, что владелец счёл более рискованным именно для первого вызова.

Почему не MSVC: в системе не нашлось `cl.exe`/Visual Studio Build Tools (`vswhere.exe` не находит
установки); MinGW-w64 (`D:\tools\mingw64\bin\g++.exe`, GCC 16.1.0, `x86_64-w64-mingw32`, SEH exception
model) — уже установлен и производит корректный x64 Windows PE DLL. x64 Windows ABI — единственная
calling convention для всех модулей независимо от компилятора, поэтому DLL, собранная MinGW, вызывает
код `MISERY-Win64-Shipping.exe` (собранного MSVC) без проблем совместимости на уровне вызова функций.

**Важная поправка, найденная эмпирически в этой же сессии, ДО первого касания игрового процесса:**
MinGW `g++` НЕ поддерживает ключевые слова MSVC `__try`/`__except` (проверено — не компилируется ни
без флагов, ни с `-fms-extensions`). Используется портируемая замена: `AddVectoredExceptionHandler`
+ `setjmp`/`longjmp`, отрепетированная целиком (см. «Офлайн-проверка» ниже) против отдельного
тестового процесса ПЕРЕД тем, как `probe.cpp` был впервые направлен на реальную игру.

## Как запускать, какие флаги включены

```
python research/instruments/ipp/ipp_controller.py [--allow-call IsSteamDeck] [--run-dir DIR]
```

Без `--allow-call` — **discovery-only режим**: резолвит live-адреса (`UClass`, `ClassDefaultObject`,
`UFunction`, указатель `ProcessEvent`) чтением памяти через уже проверенные, неизменённые функции
`research/instruments/eri/eri.py` (`run_i01`..`run_i05`), сверяет их против уже закреплённого ABI
(`LOG-0056`/`LOG-0057`), и печатает результат — **ни одного write/execute вызова Win32 API не
делается**. Это ровно то, что должно быть проверено перед первым живым вызовом (build identity,
целевой `UObject`/CDO, целевой `UFunction`, слот/адрес `ProcessEvent`, `ParmsSize`,
`ReturnValueOffset`) — offline-часть чеклиста владельца.

С `--allow-call IsSteamDeck` — включает `P-02` целиком: собирает `probe/probe.cpp` заново (MinGW,
`-Wall -Wextra -Wshadow -Wconversion`, «compile cleanly» проверяется на каждом запуске, а не
предполагается по устаревшему артефакту), инжектирует, делает РОВНО ОДИН вызов, читает результат,
выгружает DLL (`FreeLibrary`, тот же запуск), подтверждает выгрузку по списку модулей целевого
процесса. Любое другое строковое значение `--allow-call` отвергается кодом.

`--allow-mount`/`--allow-spawn` **не реализованы физически** в этом файле — их нет ни в парсере
аргументов, ни где-либо ещё в коде.

Каждый запуск (с `--allow-call` или без) пишет `research/instrument-runs/<timestamp>/manifest.json`
по схеме `research/schema/instrument-run-manifest.schema.json`, и (только при `--allow-call`)
`verify_install_before.json`/`verify_install_after.json` в тот же каталог.

## Офлайн-проверка, выполненная перед первым живым запуском

Весь механизм инъекции отрепетирован целиком (не только спроектирован) против отдельных, безопасных
тестовых процессов (`notepad.exe`, собственный тривиальный `.exe`) — ДО того, как `probe.cpp` был
хоть раз собран против реальных адресов игры. В процессе репетиции найдены и исправлены четыре
реальных дефекта, которые проектирование "на бумаге" не поймало бы:

1. Отсутствие явных `argtypes` у `ctypes`-обёрток `WriteProcessMemory`/др. молча усекало 64-битные
   указатели до 32 бит.
2. `GetExitCodeThread` возвращает 32-битный `DWORD` — классический приём «вернуть `HMODULE` через
   exit code потока» ненадёжен на x64 Windows именно поэтому; заменён на резолюцию реальной базы
   модуля через `CreateToolhelp32Snapshot`/`Module32FirstW` (тот же приём, что уже использует
   `eri.py`'s `find_module_in_process`).
3. MinGW не поддерживает `__try`/`__except` — заменено на `AddVectoredExceptionHandler` +
   `setjmp`/`longjmp`, повторно отрепетировано с намеренно битым указателем: процесс не падает,
   `RunProbe` возвращает `status=2` (исключение поймано) с корректным `exception_code`.
4. `thread_local` для состояния VEH-обработчика ненадёжен для DLL, загруженной ПОЗДНО (через
   `LoadLibrary` после старта процесса, а не при запуске) — заменено на обычные `static`, поскольку
   `RunProbe` в принципе никогда не вызывается больше чем одним потоком одновременно.

Offset `UClass::ClassDefaultObject` (`+0x110`) выведен из исходников UE 5.4.4 (`Class.h`, CL
35576357, Shipping/non-editor) ДВУМЯ независимыми агентами в этой же сессии — оба сошлись на одном и
том же значении и оба воспроизвели уже подтверждённые вживую контрольные точки
(`UStruct::Children`=`+0x48`, `UStruct::ChildProperties`=`+0x50`) без единой подгонки. Живая
проверка непосредственно этого офсета (самосогласованность: `CDO->ClassPrivate == UClass`) — часть
`resolve_target()` в `ipp_controller.py`, выполняется на КАЖДОМ запуске, до любого write/execute
вызова.

## Чему из этого кода нельзя подражать в Phase 2

* **`EXPECTED_BUILD_SHA256`, `CLASS_DEFAULT_OBJECT_OFFSET`, `PROCESSEVENT_VTABLE_SLOT`,
  `ALLOWED_FUNCTION_NAMES` как захардкоженные константы одной сборки одной игры.** Продукт должен
  резолвить всё это в рантайме (или через явную конфигурацию с собственной верификацией), не нести
  зашитые смещения одной когда-то исследованной сборки — то же предупреждение, что и у ERI,
  унаследовано дословно.
* **`build_probe_dll()` собирает DLL заново на каждом запуске вызовом `subprocess.run(g++...)`
  напрямую с абсолютным путём к конкретной установке MinGW на конкретной машине разработчика.**
  Годится для одноразового research-инструмента ровно одного человека; продукту нужна нормальная
  система сборки.
* **`--allow-call` со списком из одного жёстко прошитого имени функции.** Это осознанно узкий,
  временный, максимально безопасный дизайн для ПЕРВОГО эксперимента — не образец API для generic
  invoker'а, которого этот код намеренно не реализует.
* **Отсутствие ретраев/устойчивости к сбоям.** Любая ошибка на любом шаге — `Blocked`, немедленная
  остановка, отчёт. Правильно для research (честный отказ лучше угадывания), неприемлемо для
  продукта, которому нужна осмысленная деградация.
* **VEH + `setjmp`/`longjmp` как единственный уровень защиты от падения.** Работает для ОДНОГО
  контролируемого вызова с уже провалидированными указателями; не масштабируется на произвольный,
  многократный, конкурентный вызов кода движка — это не универсальный crash-guard.
