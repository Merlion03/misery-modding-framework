## RESEARCH ONLY — NOT PRODUCTION

Это пометка, обязательная по plan.md §8.1, и она относится ко всему, что здесь когда-либо
появится. Правило секции: **ни ERI, ни IPP не наследуются продуктом**. Код обоих живёт в
`research/instruments/`, а не в `src/`, и в Phase 2 создаётся **новый** проект, а не рефакторинг
любого из них. В `docs/phase1-report.md` обязателен раздел «чему из ERI/IPP нельзя подражать».

Свойства, которые здесь считаются нормой, а в продукте были бы дефектом (plan.md §8.1):
одноразовость и выбрасываемость, отсутствие какой-либо стабильности API, и обработка ошибок в
режиме «падать громко и сразу», а не «деградировать безопасно».

## Что здесь будет

Отдельный процесс, который открывает процесс игры **с правами только на чтение**
(`PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`), перечисляет модули и читает память. Он
**ничего не пишет, ничего не инжектит, не ставит хуков и не вызывает функций игры** — это
архитектурное свойство, а не настройка (plan.md §8.2).

Это уровень 1 инструментария и точка, с которой начинается любое наблюдение за живой игрой.
Правило по умолчанию plan.md §8.4: **если задачу можно решить уровнем 1 хотя бы дороже — она
решается уровнем 1.** Экономия времени исследователя основанием для перехода на уровень 2 не
является.

## Правила, действующие для запуска (plan.md §8.5)

* Инструмент запускается **только** против полностью контролируемых сессий (решение D-05).
  Никаких публичных лобби.
* Все дампы пишутся в `research/` этого репозитория и **никогда** в папку игры (решение D-01).
* Ни один инструмент не устанавливается «навсегда»: постоянное присутствие наших файлов в папке
  игры запрещено.
* Каждый запуск пишет манифест в `research/instrument-runs/<timestamp>/manifest.json` — см.
  `research/instrument-runs/README.md`.

## Что означает «достаточно»

plan.md §8.6, exit criteria M3: ERI выдаёт `classes.jsonl` с непустым `/Script/MISERY`,
воспроизводимо, **без единой записи в память процесса** и без записи чего-либо в папку игры.

Обратить внимание, что критерий здесь предъявляется к способу получения результата не меньше, чем
к результату. Дамп, полученный записью в процесс, критерий не выполняет — он его нарушает.

## Технология и почему выбрана (ответ на Q-8.1)

**Python + `ctypes`, вызывающий Toolhelp32/`OpenProcess`-семейство Win32 API напрямую.**
Критерий plan.md §8.6 Q-8.1 — «минимальная стоимость до первого дампа» — тот же, которым
руководствовался каждый инструмент этого репозитория. `ctypes` — часть стандартной библиотеки, то
есть новой зависимости рантайма не появляется; язык — тот же, что у всей остальной оснастки
(`tools/`, `pyghidra_scripts/`), значит вспомогательный код (JSON-сериализация, `pathguard`,
конвенция `--recorded-at`/`--no-timestamp`) переиспользуется, а не пишется заново на Rust или C++.
Rust и C++ (альтернативы, названные в Q-8.1) были бы быстрее в рантайме, но дороже до первого
рабочего дампа — а именно эта стоимость и есть критерий, а не будущая производительность
инструмента, который по определению одноразовый (plan.md §8.1).

## Как запускать

```
python research/instruments/eri/eri.py \
    --run-dir research/instrument-runs/<timestamp>
```

Это нормальный, предпочтительный способ запуска: `--build-key` **не нужен**. Инструмент сам
вычисляет sha256 файла, который ОС-загрузчик реально отобразил для найденного процесса
(`module.exe_path` из `MODULEENTRY32W`, потоково, без загрузки ~130 МБ файла в память целиком —
см. `establish_build_identity()`/`compute_file_sha256()` в `eri.py`), и использует этот
самостоятельно вычисленный хэш как авторитетный `build_key` и в документе I-01, и в манифесте.

`--run-dir` — это удобство: подставляет `--out <run-dir>/i01-process-info.json` и
`--manifest-out <run-dir>/manifest.json`, если они не заданы явно, и берёт `run_id` манифеста из
имени этого каталога (см. `research/instrument-runs/README.md`). Оба пути можно задать и вручную
через `--out`/`--manifest-out`, если удобнее другое расположение внутри `research/`.

Полезные флаги:

* `--process-name` — по умолчанию `MISERY-Win64-Shipping.exe`; сравнение всегда **точное**,
  регистронезависимое, никогда не подстрока (см. «Что инструмент принципиально не делает» ниже —
  здесь это ещё и требование корректности, не только архитектуры).
* `--build-key` — **ОПЦИОНАЛЬНАЯ ПЕРЕКРЁСТНАЯ ПРОВЕРКА**, не источник истины. Формат —
  `sha256:<64 hex>`, тот же, что в `research/schema/kb-record.schema.json`. Если задан, он
  сравнивается с самостоятельно вычисленным хэшем этого прогона; при совпадении прогон продолжается
  и в вывод пишется, что значение **независимо подтверждено**, а не просто заявлено; при
  несовпадении прогон падает громко с `BuildKeyMismatchError` (называя оба значения), **до** записи
  любого файла вывода. Кэшированный/переданный `build_key` запрещён как источник истины —
  см. раздел «Почему identity всегда self-established» ниже.
* `--recorded-at ISO8601` — фиксирует таймстемп и в документе I-01, и в манифесте, для
  побайтово воспроизводимого прогона.
* `--no-timestamp` — обнуляет `recorded_at` **только** в документе I-01 (два прогона в разные
  каталоги дают побайтово идентичный JSON); на манифест не влияет, потому что
  `instrument-run-manifest.schema.json` требует непустой `recorded_at`/`executed_at` всегда — для
  детерминированного манифеста тоже нужен `--recorded-at`.
* `--json` — печатает короткую машиночитаемую сводку в stdout вместо человеко-читаемых строк в
  stderr.

**I-02** включается флагом `--run-i02` (в той же команде, что и I-01 — I-02 нуждается в
`base_address`/`image_size_bytes` из I-01 этого же прогона, отдельно не запускается):

```
python research/instruments/eri/eri.py \
    --run-dir research/instrument-runs/<timestamp> \
    --run-i02
```

Пишет `<run-dir>/i02-guobjectarray.json` и добавляет `"I-02"` в `capabilities_enabled` манифеста.
Три проверки — те же, что названы в `research/evidence/RF-05/README.md`'s «What a runtime
observation would need to show to move this above HYPOTHESIS»: (1) `NumElements`/`MaxElements`
правдоподобны; (2) выборка живых индексов — вычислен адрес `FUObjectItem.Object`, и первые 8 байт
самого объекта (vtable-указатель) попадают в диапазон образа модуля; (3) два чтения `NumElements`,
разделённых по времени, не убывают. **Опровержение кандидата — это валидный, отчитываемый
результат исследования, а не сбой инструмента**: при провале одной или нескольких проверок
`main()` всё равно завершается кодом 0 и пишет документ с `"structurally_consistent": false` —
инструмент падает громко (`ReadProcessMemoryFailedError`, ничего не записывается) только когда сам
не смог прочитать память (аппаратный сбой Win32-вызова или неполное чтение), а не когда прочитанные
значения оказались неправдоподобными.

Полезные флаги I-02: `--guobjectarray-rva HEX` (по умолчанию — RF-05 кандидат, `0x7a78ed0`);
`--i02-sample-size N` (по умолчанию 32); `--i02-poll-interval-seconds SECONDS` (по умолчанию 2.0);
`--i02-max-scan-indices N` (жёсткий потолок на число просмотренных индексов, чтобы испорченный
`NumElements` не превратил выборку в неограниченное сканирование); `--i02-out PATH`.

Живого процесса игры на этих прогонах не было (не запускался и не должен запускаться в среде
разработки без игры) — интеграционный прогон против реального `MISERY-Win64-Shipping.exe`
выполняется отдельно, вручную, тем, у кого игра действительно запущена; для I-02 это отдельно
и то, что устанавливает реальный вердикт по кандидату из RF-05 (см. статус вверху файла).

**I-03** включается флагом `--run-i03` (в той же команде, что и I-01 — как и I-02, отдельно не
запускается):

```
python research/instruments/eri/eri.py \
    --run-dir research/instrument-runs/<timestamp> \
    --run-i03
```

Пишет `<run-dir>/i03-fnamepool.json` и добавляет `"I-03"` в `capabilities_enabled` манифеста.
Реализует первые два шага из `research/evidence/RF-06/README.md`'s «What a runtime observation
would need to show to move this above HYPOTHESIS»: (1) читает `bNamePoolInitialized` и честно
сообщает, ненулевой ли он; (2) декодирует `FNameEntryId` (по умолчанию `0` — `EName::None`,
единственный id с известным ожидаемым ответом) через кандидатный `FNamePool` и сверяет результат с
литеральным текстом `"None"` — поле `decoded_as_expected` в выводе. Несовпадение — валидное,
отчитываемое опровержение кандидата RF-06 или битовой раскладки заголовка, а не сбой инструмента
(та же дисциплина, что у I-02 — см. «STRUCTURAL REFUTATION IS A RESULT, NOT AN ERROR» в `eri.py`).

Полезные флаги I-03: `--namepool-rva HEX` / `--name-pool-initialized-rva HEX` (по умолчанию —
кандидаты RF-06, `0x79c2180` / `0x7995e5e`); `--i03-name-entry-id ID` (по умолчанию `0`); `--i03-out
PATH`.

Третий шаг из RF-06's списка — сверка с живым `UObject`, найденным через I-02, — реализован как
bounded-проба «/Script/MISERY live reflection», флаг `--run-i03-reflection` (требует **и**
`--run-i02`, **и** `--run-i03` в этом же прогоне — иначе прогон падает громко ещё до открытия
хендла):

```
python research/instruments/eri/eri.py \
    --run-dir research/instrument-runs/<timestamp> \
    --run-i02 --run-i03 --run-i03-reflection
```

Читает NamePrivate.ComparisonIndex (первые 4 байта `FName`, смещение `0x18` в `UObjectBase` —
выведено из `UObjectBase.h` и перекрёстно проверено против собственной находки RF-05 по
`InternalIndex==+0xc`) у ограниченной выборки живых объектов, найденных через ту же
shift-16/mask-0xFFFF/stride-24 арифметику, что и I-02's chunk walk, и декодирует каждое имя через
I-03. Ищет буквальное `"MISERY"` — собственное имя `UPackage`-объекта, НЕ полный путь
`/Script/MISERY` (сборка полного пути через цепочку Outer — вне рамок этой пробы). **Честно, явно:
это правдоподобный, НЕ исчерпывающий поиск** — живая вселенная `UObject` в запущенной игре, скорее
всего, десятки тысяч объектов, и промах (`misery_found: false`) в ограниченной выборке — это не
доказательство отсутствия, а лишь «не найдено среди осмотренных объектов»; поле `note` в выводе
несёт эту оговорку в самих данных, а не только в докстринге. Полезные флаги:
`--i03-reflection-sample-size N` (по умолчанию 512 — больше, чем `--i02-sample-size`, потому что
это поиск одного конкретного объекта, а не статистическая выборка), `--i03-reflection-max-scan-
indices N`, `--name-private-offset HEX` (переопределение производного смещения `0x18`).

## Почему identity всегда self-established, а не просто заявлена (LOG-0048/LOG-0049)

**2026-08-27**: оператор запустил инструмент против живого `MISERY-Win64-Shipping.exe` и передал
`--build-key`, скопированный из более ранней статической работы, не перепроверив его. В тот же
момент Steam незаметно обновил игру как побочный эффект её запуска (`steam_buildid`
24826585 → 24953925). Переданный `build_key` оказался НЕВЕРНЫМ для реально читаемого процесса —
ошибка вскрылась только позже, вручную, сверкой самостоятельно вычисленного sha256 с `buildid` из
`appmanifest_2119830.acf`, и её пришлось исправлять в уже записанных JSON-артефактах.

Правило, введённое этим проходом (обязательное для каждой live-сессии): **каждая live attach
session самостоятельно устанавливает identity текущего exe; cached/переданный `build_key` запрещён
как источник истины.** Инструмент теперь всегда сам вычисляет sha256 `module.exe_path` — того
самого файла, который ОС-загрузчик реально отобразил для найденного процесса — и использует его как
`build_key`, если `--build-key` не передан, или сверяет с ним переданное значение, если оно есть
(`BuildKeyMismatchError` при несовпадении, до единой записи на диск). Оба выходных документа несут
это структурно, а не только в докстринге: поля `identity_self_established` (всегда `true`) и
`build_key_cross_checked` (было ли переданное значение независимо подтверждено, а не просто
принято на веру).

Дополнительно, чисто информационно и read-only: `known_build`/`build_id` — найден ли этот
самостоятельно вычисленный `build_key` в `research/builds/index.json`, и если да, под каким
`build_id`. Это не меняет, что читает I-01 (`base_address`/`image_size_bytes` одинаковы для
известной и неизвестной сборки), и никогда не служит основанием подтягивать RVA/адрес/сигнатуру из
`research/evidence/` **другой** сборки — неизвестная сборка не наследует bindings/candidates
предыдущей версии, и известная тоже не наследует их через один этот факт.

## Что инструмент принципиально не делает (и почему это архитектурно)

plan.md §8.2: «ничего не пишет, ничего не инжектит, не ставит хуков, не вызывает функций игры».
Это доказуемо из кода, а не только заявлено в докстринге, двумя фактами, которые может проверить
рецензент, не доверяющий этому README:

1. **Полный список Win32-вызовов этого прохода — восемь функций**, и все восемь — вызовы
   наблюдения без побочных эффектов: `CreateToolhelp32Snapshot`, `Process32FirstW`,
   `Process32NextW`, `Module32FirstW`, `Module32NextW`, `OpenProcess`, `ReadProcessMemory` (с I-02,
   переиспользуется I-03 — не девятая функция), `CloseHandle`. Ни `WriteProcessMemory`, ни
   `VirtualAllocEx`/`VirtualProtectEx`, ни `CreateRemoteThread`/`NtCreateThreadEx`, ни
   `SetWindowsHookEx` — нигде в файле. `ReadProcessMemory` только читает и не требует никаких прав
   сверх `PROCESS_VM_READ`, который уже есть у хендла (см. пункт 2). `tests/test_eri_i01.py`
   фиксирует отсутствие запрещённых имён как вызовов, так что случайное появление одного из них в
   будущей правке провалит тест.
2. **Ровно одна точка вызова `OpenProcess`** — метод `Win32Api.open_process` в `eri.py` — и маска
   прав, которую он передаёт, это единственная константа модуля `PROCESS_ACCESS_RIGHTS =
   PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (`0x0410`), никогда не параметр и не вычисляемое
   значение, **неизменная добавлением I-02 и I-03**. Ни `PROCESS_ALL_ACCESS`, ни `PROCESS_VM_WRITE`,
   ни `PROCESS_VM_OPERATION`, ни `PROCESS_CREATE_THREAD`. Аналогично — **ровно одна точка вызова
   `ReadProcessMemory`** (метод `Win32Api.read_process_memory`), использующая тот же самый хендл,
   что I-01 уже открывает через пункт выше; I-03's `decode_fname_entry_id`/`sample_object_names`
   вызывают её через тот же метод, а не заводят вторую обёртку. Рецензенту, чтобы проверить оба
   утверждения, достаточно прочитать по одной строке на каждое; `tests/test_eri_i01.py::
   test_source_has_exactly_one_openprocess_call_site`, `test_process_access_rights_is_query_and_vm_read_only`,
   `tests/test_eri_i02.py::test_source_has_exactly_one_readprocessmemory_call_site` и
   `tests/test_eri_i03.py::test_source_still_has_exactly_one_readprocessmemory_call_site` закрепляют
   все три факта как тест, а не только как утверждение в тексте.

Хуков нет по той же причине, что и записи: ни один системный или пользовательский хук
(`SetWindowsHookEx`, детур, патч IAT/EAT) нигде не устанавливается — единственное взаимодействие с
целевым процессом — это чтение его таблицы модулей через Toolhelp32, что не требует и не даёт
возможности исполнить что-либо внутри процесса. Вызовов функций игры нет по построению: у
инструмента нет ни одного способа исполнить код в чужом адресном пространстве (для этого нужны
права вроде `PROCESS_CREATE_THREAD`/`PROCESS_VM_OPERATION`, которых маска прав не содержит) и он
не пытается — I-01 останавливается на чтении `modBaseAddr`/`modBaseSize` из уже готовой,
предоставленной ОС таблицы.

## Известные ограничения

* **PID — не стабильный идентификатор между прогонами.** Windows переиспользует PID; тот же
  MISERY, перезапущенный, получит другой. `pid` в документе I-01 полезен только для корреляции
  внутри одной живой сессии; воспроизводимая идентичность записи — это `build_key` +
  `recorded_at`, не `pid`. Отмечено и в докстринге `build_i01_document`.
* **`base_address` — ASLR-случаен на каждый запуск игры, и это ожидаемо, а не баг.** Если у вас
  есть кандидатный адрес из статического анализа (RVA/VA из RF-05/RF-06/RF-07, полученные против
  образа НА ДИСКЕ), это **не то же самое число**, что `base_address_decimal` этого инструмента.
  Чтобы получить реальный VA в памяти живого процесса, нужно **base_address (этот прогон) + RVA**,
  и приравнивать `image_base_from_static_analysis` к `base_address` без этого сложения нельзя —
  только если ASLR случайно не поставил образ на тот же адрес, чего предполагать не следует.
* **Обновлено 2026-08-27**: интеграционный прогон против реального `MISERY-Win64-Shipping.exe`
  выполнен (`research/instrument-runs/2026-08-27T130426Z/`, воспроизведён дважды) — реальный
  `Win32Api` со структурами `ctypes` подтверждён рабочим против живого процесса, независимо
  перепроверен сверкой `image_size_bytes` с `SizeOfImage` из PE-заголовка файла на диске. См.
  `RESEARCH_LOG.md` LOG-0048 для полного отчёта, включая обнаруженное по ходу обновление игры
  Steam-ом.
* `--no-timestamp` не делает манифест детерминированным сам по себе — `recorded_at`/`executed_at`
  манифеста обязаны быть непустой строкой по
  `research/schema/instrument-run-manifest.schema.json` (эта строка наследуется из
  `kb-record.schema.json`'s `#/$defs/envelope`, где `recorded_at` — обязательное поле без
  варианта `null`), так что для побайтово одинаковых манифестов между прогонами нужен именно
  `--recorded-at`, а не `--no-timestamp`.

## Чему из этого кода нельзя подражать в Phase 2

plan.md §8.1: этот файл одноразовый и выбрасываемый, у него нет обязательства по стабильности API,
и его обработка ошибок — «падать громко и сразу», а не «деградировать безопасно» — то есть ровно
противоположность тому, что было бы правильно в продуктовом коде. Конкретно:

* **Прямые вызовы Win32 через `ctypes`** без единого слоя абстракции над платформой — годится для
  одноразового исследовательского инструмента, но не для продукта, которому предстоит жить долго
  и, возможно, работать не только на Windows или переживать смену Win32 API между версиями ОС.
* **`raise` на каждый сбой без единой попытки восстановления** (`ProcessNotFoundError`,
  `TargetModuleNotFoundError`, `OpenProcessFailedError`, `SnapshotFailedError`) — корректно для
  инструмента, которым управляет исследователь, читающий stderr; неприемлемо для рантайма, который
  обязан «деградировать безопасно» вместо падения при, например, гонке с закрытием процесса.
* **Полное отсутствие версионирования и обратной совместимости формата вывода** — `eri.py` может
  завтра поменять форму JSON без каких-либо гарантий; продуктовый код обязан версионировать формат
  и поддерживать миграцию.
* **`Win32Api`/`FakeWin32Api` как инъекционный шов ради тестируемости без живого процесса** — сам
  приём можно перенимать где угодно, но конкретная пара классов здесь написана под ровно одну
  возможность (I-01) и не задумана как переиспользуемая библиотека для Phase 2.
