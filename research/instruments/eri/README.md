## RESEARCH ONLY — NOT PRODUCTION

Это пометка, обязательная по plan.md §8.1, и она относится ко всему, что здесь когда-либо
появится. Правило секции: **ни ERI, ни IPP не наследуются продуктом**. Код обоих живёт в
`research/instruments/`, а не в `src/`, и в Phase 2 создаётся **новый** проект, а не рефакторинг
любого из них. В `docs/phase1-report.md` обязателен раздел «чему из ERI/IPP нельзя подражать».

Свойства, которые здесь считаются нормой, а в продукте были бы дефектом (plan.md §8.1):
одноразовость и выбрасываемость, отсутствие какой-либо стабильности API, и обработка ошибок в
режиме «падать громко и сразу», а не «деградировать безопасно».

## Что здесь будет

Отдельный процесс, который открывает процесс игры **с правами только на чтение**
(`PROCESS_QUERY_INFORMATION | PROCESS_VM_READ`), перечисляет модули и читает память. Он
**ничего не пишет, ничего не инжектит, не ставит хуков и не вызывает функций игры** — это
архитектурное свойство, а не настройка (plan.md §8.2).

Это уровень 1 инструментария и точка, с которой начинается любое наблюдение за живой игрой.
Правило по умолчанию plan.md §8.4: **если задачу можно решить уровнем 1 хотя бы дороже — она
решается уровнем 1.** Экономия времени исследователя основанием для перехода на уровень 2 не
является.

## Правила, действующие для запуска (plan.md §8.5)

* Инструмент запускается **только** против полностью контролируемых сессий (решение D-05).
  Никаких публичных лобби.
* Все дампы пишутся в `research/` этого репозитория и **никогда** в папку игры (решение D-01).
* Ни один инструмент не устанавливается «навсегда»: постоянное присутствие наших файлов в папке
  игры запрещено.
* Каждый запуск пишет манифест в `research/instrument-runs/<timestamp>/manifest.json` — см.
  `research/instrument-runs/README.md`.

## Что означает «достаточно»

plan.md §8.6, exit criteria M3: ERI выдаёт `classes.jsonl` с непустым `/Script/MISERY`,
воспроизводимо, **без единой записи в память процесса** и без записи чего-либо в папку игры.

Обратить внимание, что критерий здесь предъявляется к способу получения результата не меньше, чем
к результату. Дамп, полученный записью в процесс, критерий не выполняет — он его нарушает.

## Технология и почему выбрана (ответ на Q-8.1)

**Python + `ctypes`, вызывающий Toolhelp32/`OpenProcess`-семейство Win32 API напрямую.**
Критерий plan.md §8.6 Q-8.1 — «минимальная стоимость до первого дампа» — тот же, которым
руководствовался каждый инструмент этого репозитория. `ctypes` — часть стандартной библиотеки, то
есть новой зависимости рантайма не появляется; язык — тот же, что у всей остальной оснастки
(`tools/`, `pyghidra_scripts/`), значит вспомогательный код (JSON-сериализация, `pathguard`,
конвенция `--recorded-at`/`--no-timestamp`) переиспользуется, а не пишется заново на Rust или C++.
Rust и C++ (альтернативы, названные в Q-8.1) были бы быстрее в рантайме, но дороже до первого
рабочего дампа — а именно эта стоимость и есть критерий, а не будущая производительность
инструмента, который по определению одноразовый (plan.md §8.1).

## Как запускать

```
python research/instruments/eri/eri.py \
    --build-key sha256:<64 hex, sha256 MISERY-Win64-Shipping.exe> \
    --run-dir research/instrument-runs/<timestamp>
```

`--run-dir` — это удобство: подставляет `--out <run-dir>/i01-process-info.json` и
`--manifest-out <run-dir>/manifest.json`, если они не заданы явно, и берёт `run_id` манифеста из
имени этого каталога (см. `research/instrument-runs/README.md`). Оба пути можно задать и вручную
через `--out`/`--manifest-out`, если удобнее другое расположение внутри `research/`.

Полезные флаги:

* `--process-name` — по умолчанию `MISERY-Win64-Shipping.exe`; сравнение всегда **точное**,
  регистронезависимое, никогда не подстрока (см. «Что инструмент принципиально не делает» ниже —
  здесь это ещё и требование корректности, не только архитектуры).
* `--build-key` — обязателен, дефолта нет: инструмент не может сам знать, на какую сборку он
  нацелен. Формат — `sha256:<64 hex>`, тот же, что в `research/schema/kb-record.schema.json`.
* `--recorded-at ISO8601` — фиксирует таймстемп и в документе I-01, и в манифесте, для
  побайтово воспроизводимого прогона.
* `--no-timestamp` — обнуляет `recorded_at` **только** в документе I-01 (два прогона в разные
  каталоги дают побайтово идентичный JSON); на манифест не влияет, потому что
  `instrument-run-manifest.schema.json` требует непустой `recorded_at`/`executed_at` всегда — для
  детерминированного манифеста тоже нужен `--recorded-at`.
* `--json` — печатает короткую машиночитаемую сводку в stdout вместо человеко-читаемых строк в
  stderr.

Живого процесса игры на этом прогоне не было (не запускался и не должен запускаться в среде
разработки без игры) — интеграционный прогон против реального `MISERY-Win64-Shipping.exe`
выполняется отдельно, вручную, тем, у кого игра действительно запущена.

## Какие I-* реализованы, какие нет

| ID | Статус |
|---|---|
| I-01 | **Реализован.** Процесс ищется точным сравнением имени exe, модуль — точным сравнением `szModule` (или basename `szExePath`), читаются `modBaseAddr`/`modBaseSize`. |
| I-16 | **Частично.** Экспорт в JSON реализован, но только для собственного вывода I-01 (`i01-process-info.json`) — это один снимок одного процесса, поэтому JSON, а не JSONL. `build_i01_document`/поле `capability` в документе спроектированы так, чтобы будущая многовозможностная версия могла добавить JSONL-экспорт (по одной строке на возможность) без переписывания этой функции — см. её docstring в `eri.py`. |

## Что инструмент принципиально не делает (и почему это архитектурно)

plan.md §8.2: «ничего не пишет, ничего не инжектит, не ставит хуков, не вызывает функций игры».
Это доказуемо из кода, а не только заявлено в докстринге, двумя фактами, которые может проверить
рецензент, не доверяющий этому README:

1. **Полный список Win32-вызовов этого прохода — семь функций**, и все семь — вызовы наблюдения
   без побочных эффектов: `CreateToolhelp32Snapshot`, `Process32FirstW`, `Process32NextW`,
   `Module32FirstW`, `Module32NextW`, `OpenProcess`, `CloseHandle`. Ни `WriteProcessMemory`, ни
   `VirtualAllocEx`/`VirtualProtectEx`, ни `CreateRemoteThread`/`NtCreateThreadEx`, ни
   `SetWindowsHookEx` — нигде в файле; даже `ReadProcessMemory` не нужен для I-01 (базовый адрес и
   размер даёт перечисление модулей, а не чтение памяти). `tests/test_eri_i01.py` фиксирует
   отсутствие этих имён как вызовов, так что случайное появление одного из них в будущей правке
   провалит тест.
2. **Ровно одна точка вызова `OpenProcess`** — метод `Win32Api.open_process` в `eri.py` — и маска
   прав, которую он передаёт, это единственная константа модуля `PROCESS_ACCESS_RIGHTS =
   PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (`0x0410`), никогда не параметр и не вычисляемое
   значение. Ни `PROCESS_ALL_ACCESS`, ни `PROCESS_VM_WRITE`, ни `PROCESS_VM_OPERATION`, ни
   `PROCESS_CREATE_THREAD`. Рецензенту, чтобы проверить это утверждение, достаточно прочитать одну
   строку; `tests/test_eri_i01.py::test_source_has_exactly_one_openprocess_call_site` и
   `test_process_access_rights_is_query_and_vm_read_only` закрепляют оба факта как тест, а не
   только как утверждение в тексте.

Хуков нет по той же причине, что и записи: ни один системный или пользовательский хук
(`SetWindowsHookEx`, детур, патч IAT/EAT) нигде не устанавливается — единственное взаимодействие с
целевым процессом — это чтение его таблицы модулей через Toolhelp32, что не требует и не даёт
возможности исполнить что-либо внутри процесса. Вызовов функций игры нет по построению: у
инструмента нет ни одного способа исполнить код в чужом адресном пространстве (для этого нужны
права вроде `PROCESS_CREATE_THREAD`/`PROCESS_VM_OPERATION`, которых маска прав не содержит) и он
не пытается — I-01 останавливается на чтении `modBaseAddr`/`modBaseSize` из уже готовой,
предоставленной ОС таблицы.

## Известные ограничения

* **PID — не стабильный идентификатор между прогонами.** Windows переиспользует PID; тот же
  MISERY, перезапущенный, получит другой. `pid` в документе I-01 полезен только для корреляции
  внутри одной живой сессии; воспроизводимая идентичность записи — это `build_key` +
  `recorded_at`, не `pid`. Отмечено и в докстринге `build_i01_document`.
* **`base_address` — ASLR-случаен на каждый запуск игры, и это ожидаемо, а не баг.** Если у вас
  есть кандидатный адрес из статического анализа (RVA/VA из RF-05/RF-06/RF-07, полученные против
  образа НА ДИСКЕ), это **не то же самое число**, что `base_address_decimal` этого инструмента.
  Чтобы получить реальный VA в памяти живого процесса, нужно **base_address (этот прогон) + RVA**,
  и приравнивать `image_base_from_static_analysis` к `base_address` без этого сложения нельзя —
  только если ASLR случайно не поставил образ на тот же адрес, чего предполагать не следует.
* **Обновлено 2026-08-27**: интеграционный прогон против реального `MISERY-Win64-Shipping.exe`
  выполнен (`research/instrument-runs/2026-08-27T130426Z/`, воспроизведён дважды) — реальный
  `Win32Api` со структурами `ctypes` подтверждён рабочим против живого процесса, независимо
  перепроверен сверкой `image_size_bytes` с `SizeOfImage` из PE-заголовка файла на диске. См.
  `RESEARCH_LOG.md` LOG-0048 для полного отчёта, включая обнаруженное по ходу обновление игры
  Steam-ом.
* `--no-timestamp` не делает манифест детерминированным сам по себе — `recorded_at`/`executed_at`
  манифеста обязаны быть непустой строкой по
  `research/schema/instrument-run-manifest.schema.json` (эта строка наследуется из
  `kb-record.schema.json`'s `#/$defs/envelope`, где `recorded_at` — обязательное поле без
  варианта `null`), так что для побайтово одинаковых манифестов между прогонами нужен именно
  `--recorded-at`, а не `--no-timestamp`.

## Чему из этого кода нельзя подражать в Phase 2

plan.md §8.1: этот файл одноразовый и выбрасываемый, у него нет обязательства по стабильности API,
и его обработка ошибок — «падать громко и сразу», а не «деградировать безопасно» — то есть ровно
противоположность тому, что было бы правильно в продуктовом коде. Конкретно:

* **Прямые вызовы Win32 через `ctypes`** без единого слоя абстракции над платформой — годится для
  одноразового исследовательского инструмента, но не для продукта, которому предстоит жить долго
  и, возможно, работать не только на Windows или переживать смену Win32 API между версиями ОС.
* **`raise` на каждый сбой без единой попытки восстановления** (`ProcessNotFoundError`,
  `TargetModuleNotFoundError`, `OpenProcessFailedError`, `SnapshotFailedError`) — корректно для
  инструмента, которым управляет исследователь, читающий stderr; неприемлемо для рантайма, который
  обязан «деградировать безопасно» вместо падения при, например, гонке с закрытием процесса.
* **Полное отсутствие версионирования и обратной совместимости формата вывода** — `eri.py` может
  завтра поменять форму JSON без каких-либо гарантий; продуктовый код обязан версионировать формат
  и поддерживать миграцию.
* **`Win32Api`/`FakeWin32Api` как инъекционный шов ради тестируемости без живого процесса** — сам
  приём можно перенимать где угодно, но конкретная пара классов здесь написана под ровно одну
  возможность (I-01) и не задумана как переиспользуемая библиотека для Phase 2.
