## 2. Идентичность сборки: `build_key`, `content_key`, `build_id`

Определения — plan.md 3.2. Смысл разделения: Steam `buildid` может измениться без
изменения исполняемого файла, и наоборот, поэтому Steam-номер **не** является
идентичностью.

### `build_key` — первичная, каноническая идентичность

```
build_key = sha256( MISERY/Binaries/Win64/MISERY-Win64-Shipping.exe )
```

Значение для этой сборки:

```
sha256:0eef3715244b467c830022c4260a0e2c29c7def1429cb34aa37fdf9b7e14a383
```

Хранится с префиксом `sha256:` — это форма, требуемая
`kb-record.schema.json#/$defs/build_key`, и она же используется как имя ключа в
`research/builds/index.json`. **Все записи базы знаний ссылаются на `build_key`, а не
на `build_id`**, потому что `build_key` не меняется при переименованиях директорий.

Источник — именно Shipping-образ (134 658 048 байт, 9 PE-секций; число секций
перепроверено инструментом F-01, см. §5). Второй файл
`MISERY/Binaries/Win64/MISERY.exe` (282 826 240 байт, 10 секций, включая `.uedbg`)
идентичностью **не** является: decision **D-04** — только read-only oracle, и тезис
«Development build» остаётся HYPOTHESIS (confidence 0.65), а не фактом.

### `content_key` — идентичность контента

```
content_key = sha256( concat( sha256 всех .utoc ) )
```

Значение:

```
sha256:55ff0e5f605d4777863bd6b061332eaf351da5800dc80c6f826547c2722f9039
```

Правило упорядочивания (зафиксировано и в поле `notes` самого артефакта): конкатенация
lowercase hex-дайджестов sha256 каждого `.utoc`, в ASCII, без разделителей, при
сортировке по нормализованному пути по возрастанию. Вклад дали два файла:
`MISERY/Content/Paks/MISERY-Windows.utoc`, затем `MISERY/Content/Paks/global.utoc`.

Зачем отдельно: если exe не изменился, а контейнеры изменились — это **патч только
контента**, и он виден как новый `content_key` при том же `build_key`. Обратный случай
(патч кода) даёт новый `build_key`.

### `build_id` — читаемое имя и имя директории

```
build_id = "misery-" + <steam_buildid> + "-ue" + <engine_version> + "-" + <build_key[0:12]>
         = "misery-" + 24826585 + "-ue" + 5.4.4 + "-" + 0eef3715244b
         = misery-24826585-ue5.4.4-0eef3715244b
```

`build_key[0:12]` — это первые 12 символов **чистого hex-дайджеста**, без префикса
`sha256:`.

**`build_id` НЕ изменился, и записи в `aliases` не потребовалось.** Прежняя редакция
этого раздела предупреждала: «`build_id` содержит `ue5.4.4`, то есть provisional версию
движка; если M1 уточнит версию, `build_id` изменится, а прежнее имя обязано попасть в
`aliases`». Предупреждение сохранено как superseded: M1.5 **подтвердил** 5.4.4, значит
подстрока в имени осталась той же, `aliases` остаётся пустым, и переименование
директории не выполнялось. Предупреждение перестало быть прогнозом, но правило, которое
оно описывало, остаётся в силе для будущих сборок.

### `tree_hash`

```
4bc6d70c6bb6d47af6817d42b699f818609625af81f2c61d98e678661bc09959
```

sha256 по канонической сериализации строк инвентаря: для каждой строки, отсортированной
по `path`, байты `'<path>\n<size>\n<sha256>\n'` в UTF-8. Совпадение с `layout.tree_hash`
в `fingerprint.json` — **выполнено, а не ожидается**: прогон F-03 пересчитывает
`tree_hash` заново обходом установки и печатает результат сравнения как проверку
`tree_hash_matches_install_inventory` (PASS 2026-08-23). Там же сравниваются `build_key`,
`content_key`, `build_id` и построчно все 53 файла по пути, размеру и sha256
(`identity_matches_build_index/*`, `layout_matches_install_inventory`).

### 4.3 Проверка воспроизводимости

Критерий выхода: два прогона по неизменному дереву дают **побайтово одинаковый** вывод,
за исключением поля `generated_at`.

```

D:\Tools\venv-research\Scripts\python.exe tools\inventory\snapshot_install.py --out %TEMP%\inv-b.json

```

Ожидаемый результат: расхождение ровно в одной строке — `generated_at`. Проверено
2026-08-22: два прогона дали 2 изменённые строки в `diff` (по одной `-`/`+`), и после
удаления `generated_at` документы совпали побайтово; `tree_hash` был стабилен.

Для `fingerprint.json` то же проверено 2026-08-23 двумя способами: флагом
`--selftest-reproducible` (документ строится дважды в одном процессе) и двумя отдельными
прогонами с `diff` — расхождение ровно в одной строке, `identity.generated_at`;
`anomalies.md` расходится ровно в одной строке по той же причине.

**Одно известное исключение, измеренное, а не предположенное.** Поле
`steam.appmanifest_sha256` может законно различаться между двумя прогонами: Steam
перезаписывает `appmanifest_2119830.acf` по своему расписанию. Самопроверка не прощает
этот указатель списком — она **перечитывает** манифест и признаёт различие только если
перечитывание подтвердило, что файл действительно изменился, после чего маскирует
указатель и сравнивает документы ещё раз, чтобы «всё остальное совпало» было проверкой,
а не фразой. Ничто, вычисленное из самой установки (`build_key`, `content_key`,
`tree_hash`, любой дайджест, любое поле заголовка), не варьируется.

## 6. Ограничения этого baseline

* `install-inventory.json` фиксирует состояние **на 2026-08-22T12:19:17Z**,
  `fingerprint.json` — **на 2026-08-23T13:42:12Z**. Любое обновление игры через Steam
  делает baseline устаревшим; признак — изменение `build_key` (патч кода) или
  `content_key` (патч контента) при повторном прогоне. На 2026-08-23 обе величины
  пересчитаны заново и совпали с записанными.
* Инвентарь содержит только файлы; директории строками не являются, поэтому
  `file_count = 53` считает именно файлы.
* `mtime` в артефакте — UTC с точностью до микросекунд, вычисляется из `st_mtime_ns`
  целочисленной арифметикой, поэтому в документ не попадает погрешность float.
  Локальное время не используется намеренно: иначе инвентарь не был бы воспроизводим
  между машинами.
* Пользовательские данные (`%LOCALAPPDATA%\MISERY\Saved\...`) в инвентарь **не**
  входят — это не часть установки. Каталог `Logs` при recon был пуст, что само по себе
  является находкой (Shipping-сборка с подавленным логированием).
* **Этот файл — снимок, и он старел молча дважды.** Первый раз — когда в §1 остались
  строки «ожидается в M1» у трёх уже существующих артефактов и «ОТСУТСТВУЕТ» у
  существующего `install.json`; второй — когда §4.5 продолжала обещать «0 warnings»
  давно изменившегося валидатора. Правило на будущее: любое утверждение о том, что
  **появится**, обязано быть переписано в момент появления, а не оставлено рядом с
  фактом; проверяются такие утверждения при закрытии каждого milestone (plan.md 18.3
  пункт 6, сверка между документами).
