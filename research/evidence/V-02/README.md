# V-02 — crash-отчёты движка: соответствие сборке (RISK-09) и поля контекста

Метод `plan.md` §4.1 V-02. Инструмент — `tools/static/engine_version.py`.

| Файл | Что это |
|---|---|
| `crash-correspondence.json` | по одному блоку на каждый отчёт из `%LOCALAPPDATA%/MISERY/Saved/Crashes`: его собственный mtime, поля `CrashContext.runtime-xml`, запись модуля `MISERY-Win64-Shipping.exe` из `UEMinidump.dmp` и вердикт соответствия текущей сборке |

## Почему этот каталог устроен именно так

`plan.md` §4.2 требует особой осторожности: отчёт в `Saved/Crashes` мог быть создан
**предыдущей** версией игры, каждый использованный отчёт обязан сопровождаться своим
mtime, и вывод «версия текущей сборки» не может опираться только на отчёты. Здесь это
не пересказано, а **проверено**. В минидампе лежит `MINIDUMP_MODULE_LIST`, и запись
модуля `MISERY-Win64-Shipping.exe` в нём несёт `SizeOfImage`, `CheckSum`,
`TimeDateStamp` и подпись CodeView (GUID + age) того образа, который был загружен в
момент падения. Все четыре величины сравниваются с теми же четырьмя, прочитанными из
exe, лежащего на диске **сейчас**. Вердикт на отчёт — `this-build`, `other-build` или
`undecidable`, и он стоит в поле `build_correspondence`.

Итог этой проверки для текущего состояния машины записан в
`research/unreal/engine-version.md` §RISK-09. Кратко: часть отчётов принадлежит другой
сборке, и это видно по всем четырём величинам сразу, а не по одной.

## Разделение V-02a и V-02b

* **V-02a** — запись модуля из минидампа. Это разбор двоичного файла по определённым
  смещениям, то есть ровно то, для чего существует oracle `binary-analysis`. Эта
  половина **градуирована** и она несёт ответ по RISK-09.
* **V-02b** — текстовые поля XML (`EngineVersion`, `BuildConfiguration`,
  `IsSourceDistribution` и прочие). Эта половина опубликована как сырые данные и
  **не градуирована**: `research/unknowns.md` NEW-01 фиксирует, что в закрытом списке
  девяти oracle §10.5 нет класса для **содержимого** crash-отчёта, и что `external-doc`
  для него — ошибка. NEW-01 оставляет два допустимых выхода: десятый oracle или «в базу
  знаний не заносится». Инструмент закрытый список открыть не может, поэтому выбран
  второй, а решение о первом остаётся за `research/decisions.md`.

## C-13

Из XML читаются только поля, перечисленные в `V02_XML_FIELDS` инструмента. Ни
`UserName`, ни `MachineId`, ни `LoginId`, ни `EpicAccountId`, ни `CommandLine`, ни
`BaseDir`, ни `RootDir` не читаются и в артефакт не попадают. Из минидампа берутся
только базовые имена модулей — полная строка там является абсолютным путём на машине,
где произошло падение. Путь до каталога отчётов записан только в виде
`%LOCALAPPDATA%/MISERY/Saved/Crashes`.

## Оговорка об окружении

В части дампов среди загруженных модулей присутствует сторонний загрузчик скриптов.
Это оговорка **об окружении**, а не утверждение об игре: на поля версии движка она не
влияет, но означает, что процесс, который описывают эти отчёты, не был стоковым.
Обнаружение идёт только по имени модуля, поэтому загрузчик, установленный подменой
системной DLL, таким способом не виден, и отсутствие имени в списке не является
доказательством чистого процесса.
