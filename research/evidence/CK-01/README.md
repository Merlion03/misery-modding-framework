# CK-01 — читаемость `MISERY-Windows.pak` и наличие в нём cooked-пакетов

Артефакты этого каталога отвечают на вопрос, который стоит **перед** CK-01: можно ли
вообще прочитать содержимое `MISERY-Windows.pak` в границах решения D-02.

## Что здесь лежит

| Файл | Что это |
|---|---|
| `pak-index.json` | Полный документ инструмента `tools/content/pak_index.py`: футер, доказательства plaintext для трёх блоков индекса, разбор 4424 записей, четыре опровергающих пробы, слой class P (literal_reads) и слой class I |
| `pak-paths.txt` | Список всех 4424 путей: размер, размер без сжатия, флаг шифрования, индекс метода сжатия, путь. Только метаданные — ни один байт payload не читался |
| `pak-index-run1.log` | Прогон 1, с записью артефактов |
| `pak-index-run2.log` | Прогон 2, без записи. Два прогона дают идентичный JSON, кроме `generated_at` |

## Главный результат

**Все 4424 записи зашифрованы.** Флаг читается из бита 22 закодированного слова
(`IPlatformFilePak.cpp:7174`), который выставляет `FPakEntry::Flag_Encrypted == 0x01`
(`IPlatformFilePak.h:382`). Различных слов флагов в контейнере ровно **одно** —
`0xE0400000`, 4424 раза.

Незашифрованных записей — **0**, поэтому ни один payload этим прогоном не читался:
D-02 разрешает читать только то, что доказано незашифровано.

**Cooked-пакетов в контейнере нет ни одного:** `.uasset`, `.uexp`, `.umap`, `.ubulk`,
`.uptnl`, `.usmap`, `.ushaderbytecode` — по нулю. CK-01 из этого контейнера не
отвечается ни в какую сторону, ни при каком ключе.

## Почему чтение индекса не является расшифровкой (D-02)

Оракулом здесь выступает сам движок. `FPakFile::DecryptAndValidateIndex`
(`IPlatformFilePak.cpp:6489-6500`) расшифровывает буфер **тогда и только тогда**, когда
`Info.bEncryptedIndex`, и затем требует `SHA1(buffer) == StoredHash`. В этом файле
`bEncryptedIndex == 0`, и SHA1 байтов **как они лежат на диске** совпадает с
записанным хэшем для всех трёх блоков (primary 53 202, path-hash 133 821, full
directory 103 835 байт). Значит байты, которые разбирает движок, — это байты, которые
прочитали мы, без шага расшифровки между ними: иначе загрузка файла самим движком
провалилась бы. Запас проверки — 160 бит.

На payload этот аргумент не переносится, и инструмент этого не делает.

## Четыре пробы, каждая способна опровергнуть вердикт

1. `entry_flag_word_census` — перечень всех различных слов флагов с полным разбором.
   Ошибка маски в сводке невидима, в перечне — видна. Индекс метода сжатия
   перепроверяется против таблицы `CompressionMethods` футера.
2. `encoded_blob_tiling` — 4424 записи покрывают 53 088 байт блока **ровно**: разрывов 0,
   перекрытий 0. Неверная ширина полей не замостит блок точно случайно.
3. `layout_probe` — не читает ни одного флага. Зашифрованная несжатая запись занимает на
   диске `Align(Size, 16)` байт при том, что поле `Size` хранит длину открытого текста
   (`PakFileUtilities.cpp:1028, 1044-1060`); незашифрованная — ровно `Size`. Модель с
   выравниванием объясняет 2405 промежутков точно, модель без выравнивания — **0**,
   перекрытий 0, а конец последнего payload с выравниванием попадает в начало индекса
   **точно** (117 365 605), тогда как без выравнивания недостаёт 3 байт.
4. `local_header_probe` — локальный заголовок `FPakEntry`, который упаковщик пишет
   открытым текстом (`PakFileUtilities.cpp:2736`, шифруется только буфер данных, :1057 и
   :1109). Это независимая копия того же байта флагов, сделанная другим сериализатором в
   другом месте файла. Прочитано 4424 заголовка, расхождений с индексом **0**, байт
   флагов `0x01` у всех.

## Что здесь НЕ доказано

Совпадает ли набор путей pak с набором чанков IoStore: directory index
`MISERY-Windows.utoc` зашифрован и не читается, поэтому сравнение множеств путей
невозможно. Утверждение о непересечении делается только по классу содержимого.
