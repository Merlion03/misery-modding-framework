# S-01 — строковый индекс образов сборки (`tools/static/extract_strings.py`)

Каталог хранит неотредактированный вывод инструмента. Ничего здесь не правилось
руками. Рабочие копии — `strings.jsonl` и второй прогон — инструмент кладёт в
`workspace/strings/` (каталог в `.gitignore`), сюда скопированы только сводки и
протоколы.

Все файлы открывались **только на чтение** (D-01). Внутри установки игры ничего
не создавалось, не менялось и не удалялось; каждый выходной путь проходит
`tools/inventory/pathguard.check_output_path` **до** открытия файла, поэтому
отклонённый путь не оставляет за собой даже усечённого файла.

## Решение по C-13: `strings.jsonl` в репозиторий не кладётся

**Решение.** Полный `strings.jsonl` для любого игрового бинарника **не
коммитится**. В публичном репозитории лежит сводка (`*.json`), протокол
(`*.log`), счётчики, ограниченная выборка буквальных чтений класса P и sha256
самого `strings.jsonl`.

**Почему.** Три причины, каждая достаточна по отдельности.

1. `strings.jsonl` — это дословная строковая таблица игрового бинарника, то есть
   производное от файла игры содержимое, а не измерение о нём. C-13 запрещает
   держать в публичном репозитории игровые бинарники и то, что из них извлечено
   дословно; запись хэша и размера вместо файла — прямо предписанная планом
   замена.
2. Объём делает файл неревьюируемым, а `.gitignore` этого репозитория прямо
   говорит, что его ценность — **диффабельный текст**: 898 573 029 B для
   Shipping и 1 900 679 797 B для oracle, суммарно 2,8 ГБ. Такой файл нельзя
   посмотреть в pull request, и он в 20 раз больше самого образа игры.
3. Файл **воспроизводим**: два прогона дали побайтово одинаковый `strings.jsonl`
   (совпал sha256, см. ниже). Восстанавливается одной командой из образа, а
   значит, хранить его в истории git незачем.

**Проверка, что решение уже обеспечено механически, а не только на словах.**
`.gitignore` содержит правило `workspace/*` с единственным исключением
`workspace/bin/.gitkeep`, поэтому `workspace/strings/` не попадёт в индекс git
даже при `git add -A`. Инструмент делает ошибку трудной: `strings.jsonl`
пишется **только** в отдельный файл по `--jsonl-out`, никогда не в документ
`--out`, а сводка при записи печатает напоминание с именем правила.

**Что публикуется вместо содержимого.** Счётчики, гистограммы длин, перечень
областей файла, классифицированные **имена**, из которых сделаны выводы (имена
модулей `/Script/`, имена модулей и файлов из путей сборки, имена дескрипторов),
и не более восьми буквальных чтений класса P на прогон. В документе сводки нет
ни одного поля `text` из потока записей — это проверяется тестом
`test_the_jsonl_holds_one_record_per_string_and_the_summary_only_counts`.

**Отдельно проверено на персональные данные.** В путях сборки, найденных в
образах, нет ни `Users`, ни `AppData`, ни `Documents`, ни `Desktop`, ни
`OneDrive` — 0 вхождений каждого. Корни сборки (`D:\build\++UE5\Sync`,
`F:\Unreal Engine\Projects\miseryGit`, `D:\Primary`, `v:\devel\projects\oodle2`)
никого не называют по имени, поэтому публикуются как есть, без редактирования.

## Совпадение прогонов 1 и 2 по основной цели

`strings.jsonl` двух прогонов совпал **побайтово** — один и тот же sha256
`f6a44e88…`. Человекочитаемые сводки различаются в трёх местах и ни одно из них
не относится к образу игры:

```
1876 modules declared, 145097 files walked   ->  145097 files walked   (одинаково)
Timings (s): …                               ->  другие числа
written: …/shipping-strings.json             ->  …/shipping-run2.json
```

Число **объявленных модулей** одинаково в обоих прогонах — 1876, и именно оно
участвует в выводах; в этом прогоне совпало и `files_walked` (оба прогона
сделаны подряд, дерево `D:\Program Files\UE_5.4` между ними не менялось). Полные
документы совпадают везде, кроме `generated_at`, `timings_seconds`,
`noise_control.elapsed_seconds` и `ue_module_index.{elapsed_seconds,
files_scanned}` — сверка сделана обходом обоих JSON по всем ключам, других
расхождений нет.

Эта пара прогонов (и одноимённый прогон по 282-МБ oracle, и прогон по
контролю `tbbmalloc.dll`) была выполнена заново, независимо от прогона,
которым исходно наполнялся этот каталог: тот же инструмент, те же
`--out`/`--jsonl-out`/`--ue-source-root`/`--v07-plugins`/`--file-query`
аргументы, другой процесс, более поздняя дата. Все три `strings.jsonl`
совпали побайтово со значениями sha256, ранее записанными в этом файле
(таблица ниже), и структурный обход обоих JSON-документов (кроме
перечисленных volatile-полей) не нашёл ни одного расхождения — это и есть
независимое подтверждение того, что вывод инструмента детерминирован, а не
переписан вручную.

## Как спросить, есть ли конкретный файл исходника

Ответ уже вычислен и записан в документ — искать не надо:

```
python -c "import json;d=json.load(open('research/evidence/S-01/shipping-strings.json',encoding='utf-8'));print(json.dumps(d['findings']['engine_source_paths']['file_queries'],indent=2,ensure_ascii=False))"
```

Для имени, которое там ещё не спрошено, есть ключ `--file-query <имя>`
(повторяемый, регистр не важен) — он добавляет ответ в
`findings.engine_source_paths.file_queries` вместе со счётчиками вхождений,
модулем и оговоркой о том, что значит отрицательный ответ. Полный перечень имён
лежит в `findings.engine_source_paths.files`, полные пути — в
`file_examples`, разбивка по модулям — в `files_by_module`.

**Ответ на заказанный запрос.** `UnversionedPropertySerialization.cpp`:
в Shipping — **не найден**, в 282-МБ бинарнике (D-04) — **найден**, ровно одно
ASCII-вхождение, смещение 217 245 616, RVA 217 251 248, область `.rdata`,
модуль `CoreUObject`, полный литерал
`D:\build\++UE5\Sync\Engine\Source\Runtime\CoreUObject\Private\Serialization\UnversionedPropertySerialization.cpp`.
`UnversionedPropertySerialization.h` не найден ни там, ни там.
`Class.cpp` найден в обоих (в Shipping — смещение 98 927 440, RVA 98 931 024,
область `.rdata`, модуль `CoreUObject`), и служит здесь положительным контролем: он показывает, что
отрицательный ответ по первому имени — не поломка запроса.

**Что отрицательный ответ значит и чего не значит.** Он значит только одно: на
проверенной поверхности нет абсолютного пути, кончающегося этим именем. Пути
попадают в образ как остатки `__FILE__` внутри текста `check()`/`ensure()`, а
Shipping-конфигурация UE большую часть этого текста выбрасывает — что видно
прямо по числам: 589 путей в Shipping против 6 255 в oracle при вдвое большем
образе. Поэтому отсутствие пути **не** доказывает, что единица трансляции не
скомпилирована в образ. Закрывающий метод для такого вопроса — не строки:
это xref/vtable-анализ или сигнатурный поиск по коду (S-06/S-07), а не эта
поверхность.

## Проверенная поверхность и что в неё не входит

Области файла образуют полное покрытие `[0, размер)` без дыр и без пересечений;
это проверяется на каждом прогоне пробой P3. У основной цели 10 областей
(заголовки + 9 секций), overlay отсутствует, и записей без RVA — 0. У oracle 11
областей: та же раскладка плюс секция `.uedbg`, в которой инструмент нашёл 564
записи.

В поверхность **не** входит: строка, собираемая в runtime; строка, лежащая на
диске сжатой или зашифрованной; виртуальный хвост секции (на диске байтов нет);
UTF-8 multibyte, UTF-16BE и UTF-16LE вне диапазона `0x20..0x7e`. UTF-16-строка с
одним не-ASCII символом внутри попадает в индекс как два куска по обе стороны от
него, и такие куски помечены флагом `abuts_wide_non_ascii` (959 записей в
Shipping, 2 346 в oracle) — это не оценка, а перечёт.

Порог длины — 4 символа, не 8. Цена этого решения измерена, а не заявлена:
контрольный прогон по 16 МиБ детерминированных псевдослучайных байтов даёт по
длинам 4..8 отношение наблюдаемого к ожидаемому 1,175 / 0,516 / 0,433 / 0,741 /
1,083, то есть на этих длинах население **неотличимо от шума** и проба P1
честно сообщает `REFUTED THE CONCLUSION`. С длины 9 отношение 3,19, с 12 — 35,6,
с 15 — 167. Отсюда и потолок «шумовой полосы» 10, и отсюда же правило: счёт
записей — не счёт строк, у каждой записи есть `char_count` и `noise_band`, и
фильтровать по одному лишь числу записей нельзя.

## Дефекты инструмента, найденные при первом в истории запуске

Инструмент был написан в прошлом прогоне и **ни разу не запускался**. Найдено и
исправлено шесть дефектов; пять из них невидимы на файле меньше 8 МиБ, поэтому
именно запуск, а не чтение кода, был здесь методом.

| # | Дефект | Как проявлялся |
|---|---|---|
| 1 | `SCAN_WINDOW` = 8 МиБ, а окно читается вместе с lookahead одним `read_at`, у которого предел ровно 8 МиБ | падение с кодом 2 на первой же области больше 8 МиБ: «refusing a single read of 8 392 712 bytes». Прогон по образу игры был невозможен. Теперь размер окна **выводится** из предела, а тест сравнивает сумму с пределом |
| 2 | пробег, пересекающий границу окна, выдавался дважды: следующее окно видит его хвост как новый пробег с позиции 0 | дубликат записи на другом смещении, читаемый потребителем как второе вхождение. Исправлено учётом того, сколько байтов шаблон уже поглотил; отказы считаются (`runs_continued_from_a_previous_window`) |
| 3 | перенесённые через границу окна отрезки сравнивались в системе координат **предыдущего** окна | счётчик перекрытий двух кодировок расходился; на сконструированном входе — 26 вместо 24 |
| 4 | пара из двух перенесённых отрезков считалась заново в каждом окне | тот же счётчик завышался |
| 5 | проба P2 читала счётчик `utf16_low_information`, который никто не увеличивал | доля «низкоинформативных» UTF-16-пробегов всегда 0, то есть проба **не могла** опровергнуть ничего |
| 6 | проба P4 обещала в docstring два населения и проверку в обратную сторону, а делала только границы областей и только прямую | смещение, объявленное неадресуемым, никем не проверялось; выборки по индексу не было вовсе |

Отдельно — производительность, не корректность: внутренний цикл подсчёта
перекрытий строил срез списка на каждой итерации. На 134-МБ образе это давало
13+ минут; после замены среза на индекс — 41 секунда, при тех же числах.

Ещё одна правка по существу, а не по коду: UTF-16-пробег систематически
начинается на один код-юнит раньше строки, потому что байты перед широкой
строкой (последний символ предыдущей узкой строки и его терминатор) сами читаются
как пара «печатный символ, NUL». При правиле «путь обязан начинаться с начала
записи» такие записи молча теряли имя модуля. Добавлена отдельная категория
`unreal-script-path-absorbed-prefix`, имя ищется внутри записи, а число имён,
добытых только так, публикуется отдельно (58 вхождений в Shipping, 61 в oracle).

## Тесты

`tests/test_extract_strings.py`, 62 теста, все на **синтетических** PE-образах,
собранных тем же `PEBuilder`, что и `tests/test_pe_info.py` (импортируется, не
копируется). Ни один тест не читает файл игры: D-01 делает установку целью
исследования, а зависящий от неё набор тестов не воспроизводим на другой машине
и ничего не может утверждать — прогон по 134-МБ образу не отличает «в образе
1 686 933 строки» от «этот сканер печатает 1 686 933 чего угодно».

Ключевые инварианты, которые проверяются именно как инварианты, а не как
ожидаемые числа: тот же образ, просканированный окном 8 МиБ и окном 17 байт,
обязан дать **тот же** список записей и **то же** число перекрытий; перекрытий
на сконструированном входе ровно столько, сколько единиц в нём заложено.
