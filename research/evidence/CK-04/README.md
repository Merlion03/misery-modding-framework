# CK-04 — есть ли в образе код, который пересчитывает офсеты свойств при загрузке

Артефакты этого каталога отвечают на **вторую половину** CK-04. Первая половина — что делает
UE 5.4.4 — отвечается чтением first-party исходников и разобрана в
`research/packages/sp1-static-proxy.md`, раздел «CK-04». Здесь измеряется другое:

> попал ли тот код, который по исходникам управляет раскладкой, в **эту** сборку.

Это два разных акта измерения над двумя разными объектами. Дерево UE говорит, что делает движок.
Образ говорит, что было слинковано в этот исполняемый файл. Только пара говорит что-нибудь об игре.

## Что здесь лежит

| Файл | Что это |
|---|---|
| `link-path-shipping.json` | Полный документ `tools/static/link_path_probe.py` по образу, sha256 которого **и есть** `build_key`: поверхность поиска по секциям, шесть проб опровержения, слой class P (`literal_reads`), слой class I (`findings`), и `source_probes` — механически извлечённые списки членов, которые реально стримят три сериализатора |
| `link-path-shipping-run1.log` | Прогон 1, с записью артефакта |
| `link-path-shipping-run2.log` | Прогон 2, без записи. Вывод **побайтово идентичен** run1; JSON идентичен, кроме `generated_at` |
| `link-path-development.json` | То же по 282-МБ образу `MISERY/Binaries/Win64/MISERY.exe`. Статус этого образа — решение **D-04**; здесь он **подкрепление, а не основание** |
| `link-path-development-run1.log`, `-run2.log` | Два прогона, вывод идентичен |

## Главный результат

**`PATH_PRESENT_AND_REFERENCED` в обоих образах, все шесть проб PASS.**

Два обязательных литерала, каждый по одному вхождению и каждый достижимый из исполняемого кода:

| Литерал | Где он стоит в исходнике | Почему он и есть нужный маркер |
|---|---|---|
| `Class.cpp:855` | `UE_LOG(LogClass, Fatal, …)` **внутри ветки `if (bRelinkExistingProperties)`** функции `UStruct::Link` | вторая ветка той же функции вызывает `LinkWithoutChangingOffset` и не содержит ни одного `Fatal`-лога. Присутствие этого литерала — присутствие ветки, которая **пересчитывает** офсеты |
| `Property.cpp:1340` | `UE_LOG(LogProperty, Fatal, …)` внутри `OnInvalidPropertySize` | у этой функции во всём дереве **один** вызывающий, и это `FProperty::SetupOffset` — та самая функция, которая пишет `Offset_Internal = Align(OwnerStruct->GetPropertiesSize(), …)` |

Оба текста уникальны в дереве UE 5.4.4: `grep -rln` по всем `*.cpp`/`*.h` даёт по одному файлу на
каждый. Атрибуция к строке поэтому не догадка.

## Почему литерал, а не символ, и чего этот метод не доказывает

У `UStruct::Link` и `FProperty::SetupOffset` нет ни экспортируемого символа, ни RTTI-имени (S-10:
локаторов 587, классов игры среди них 0), ни импорта. Строковый литерал — то, что компилятор не
может растворить: он обязан лежать в `.rdata` побайтово, иначе форматировать нечего.

Границы, которые надо держать в голове:

* литерал в `.rdata` доказывает, что в образе есть **строка**. Что до неё доходит код — отдельная
  проверка, и она здесь выполняется: пересчёт RIP-относительных ссылок из секций с
  `IMAGE_SCN_MEM_EXECUTE`;
* ссылка доказывает, что скомпилирован **оператор**. Что оператор принадлежит именно этой функции —
  взято из дерева UE, а не из дизассемблера. Этот зазор реален, он назван, и он ровно то, что
  держит оценку `CK-04-3` на 0.88 вместо 0.95. Закрывается дизассемблированием функции вокруг
  найденной ссылки (S-05/S-06), а не новыми доводами;
* **отсутствие литерала не говорит об отсутствии функции.** Текст `check`, `checkf` и `ensureMsgf`
  вырезается при `DO_CHECK == 0` / `DO_ENSURE == 0`, что нормально для Shipping.

Последний пункт превращён из отговорки в проверку: каждая иголка помечена макросом, который её
охраняет, инструмент предсказывает, какие классы выживают при Shipping-линковке, и проба
`compile_gating_consistent` **падает**, если наблюдённая картина противоречит предсказанию.

## Наблюдённая картина различает конфигурации сама

| Образ | `UE_LOG(Fatal)` | `checkf` / `ensureMsgf` / `UE_LOG(Error)` | Чтение |
|---|---|---|---|
| `MISERY-Win64-Shipping.exe` | 2 из 2 | **0 из 4** | текст проверок вырезан — ожидаемо |
| `MISERY.exe`, 282 МБ | 2 из 2 | **4 из 4** | проверки сохранены |

То, что обе стороны совпали с предсказанием, — независимое подтверждение самой модели гейта.
Если бы `checkf`-строка нашлась там, где нет ни одного `Fatal`-текста, модель была бы перевёрнута,
и тогда ни одно «отсутствует» в этих артефактах нельзя было бы читать.

## Шесть проб, каждая способна опровергнуть вердикт

1. `required_needles_unique` — обязательная иголка отсутствует или встречается больше одного раза.
2. `required_needles_referenced` — иголка есть, но код до неё не доходит. **Здесь метод один раз
   ошибся и был исправлен:** первая версия декодировала только `lea reg,[rip+disp32]` и объявила
   литералы в 282-МБ образе недостижимыми. Настоящая причина — вторая форма ссылки: статическая
   запись лога в `.rdata`, первое поле которой — указатель на строку, а код адресует **запись**.
   Обе формы декодируются теперь и считаются **раздельно**; счёт заведомо неполный, и неполнота
   работает против вывода, а не за него.
3. `compile_gating_consistent` — картина присутствий противоречит модели компиляционного гейта.
4. `negative_control` — заведомо мутированная строка «нашлась»: матчер сообщает несуществующее.
5. `required_needles_distinct_origin` — обе иголки из одного файла, то есть одно наблюдение под
   двумя именами. (`Class.cpp` и `Property.cpp` — разные.)
6. `no_serializer_streams_the_offset` — **источниковая** проба: списки членов, реально проходящих
   через `Ar <<`, извлекаются из дерева, и в них ищется офсет. Проба умеет падать, и это
   проверено тестом `tests/test_link_path_probe.py::LinkPathProbeTests::test_serializer_probe_catches_a_streamed_offset`,
   который подсаживает `Ar << Offset_Internal` в синтетическое дерево и требует провала.

## Воспроизведение

```
python tools/static/link_path_probe.py <образ> \
    --ue-root <дерево UE 5.4.4> \
    --install-dir <корень установки> \
    [--out research/evidence/CK-04/link-path-<конфигурация>.json]
```

Только stdlib. Образ открывается на чтение; путь вывода проходит через
`tools/inventory/pathguard.py` (D-01), и внутрь установки не пишется ничего никогда.

Ни один литерал в инструменте не задан константой: все читаются из дерева UE в момент запуска
вместе с файлом и номером строки. Дерево другого changelist-а даёт предупреждение о
переформулированном сообщении, а не подставленную догадку.

## Чего в этом каталоге нет и быть не может

Подтверждения **на уровне пакета**. В установке нет ни одного читаемого cooked-пакета: CK-01
показал, что все 4424 записи `MISERY-Windows.pak` зашифрованы и cooked-пакетов там 0, а
`MISERY-Windows.utoc` — `Encrypted|Indexed` при запрете D-02 на извлечение ключа. Проверить «вот
cooked BPGC, офсета в его байтах нет» негде. Это записано как ограничение метода, а не как
оговорка: из-за него подвопрос про `FImplementedInterface::PointerOffset` остаётся `UNKNOWN`
(`sp1-static-proxy.md`, §5, CK-04-U1).
