# MISERY Modding Framework (MBPL)

[![CI](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml)

**Коротко.** Модинг-платформа для игры MISERY (Unreal Engine 5.4.4 CL 35576357,
Steam AppID 2119830). Мод — это папка с манифестом, .NET-сборкой и, при
необходимости, собственным кукнутым контентом; фреймворк загружает её в
запущенную игру, даёт публичный C#-API и убирает за ней при выгрузке.

**Публичного релиза пока нет.** В репозитории нет установщика, release-архива и
инструкции «скачай и поставь» — упаковка намеренно отложена до после Stage 10.
Всё, что описано ниже, воспроизводится из исходников на машине разработчика.

**Статус:** Stage 8 (Developer Platform Foundations) — **закрыт**.
Следующее — Stage 9 (Multiplayer Foundations). Дорожная карта — ниже.

---

## 1. Что это

MBPL — не набор патчей и не набор скриптов поверх чужого загрузчика. Это
платформа с собственным фундаментом:

* **Не зависит от UE4SS** — ни как runtime-зависимость, ни как встроенный код
  (ограничение C-04, `plan.md` §3). UE4SS допустим ровно в двух ролях: источник
  публичной документации по структурам UE и независимая точка сверки гипотез.
* **Не требует ключей, расшифрованных контейнеров и распакованной игры**
  (D-02/D-11, `docs/research-vs-product.md` §3). Мод везёт свой контент, а не
  вырезанный из игры.
* **Не переписывает игру.** Установка остаётся read-only, кроме одной явно
  спроектированной точки — bootstrap-прокси и каталога фреймворка рядом с ним.
* **Fail-closed по сборке.** Профиль привязок несёт RVA и по 16 байт кода на
  каждый адрес; байты сверяются с живой памятью перед использованием. Чужая
  сборка не «работает как-нибудь» — она отказывается стартовать.

Проект вырос из исследовательской фазы, и её дисциплина сохранена: у каждого
факта есть `oracle`, `evidence level` и `confidence`, а догадка не называется
фактом (C-07). Раздел 7 объясняет, как это читать.

## 2. Что работает сегодня

Ниже — состояние на HEAD. Колонка «готовность» различает четыре вещи, и это
различение здесь важнее самих строк.

Это **не** `evidence level` из модели доказательности: тот градуирует, насколько
хорошо известен факт об игре, а этот — насколько построена наша собственная
возможность. Слова взяты разные намеренно, чтобы две шкалы нельзя было
перепутать.

| | значение |
|---|---|
| **PROVEN** | работает в живой игре, есть принятое acceptance-доказательство |
| **NARROW** | доказано, но только для одного конкретного случая; общность не заявлена |
| **PLANNED** | спроектировано и/или запланировано, кода нет |
| **NOT IMPLEMENTED** | сознательно не сделано; см. раздел 5 |

## 3. Архитектура рантайма

```
Steam → MISERY-Win64-Shipping.exe
          │
          ├─ dwmapi.dll (bootstrap-прокси)         ← единственный файл, который мы кладём рядом
          │     проверяет fingerprint образа; при несовпадении не грузит ничего
          │
          └─ MiseryFramework/
                MiseryRuntime.dll (нативный)
                  ├─ bindings.json  RVA + 16 байт кода на адрес, сверяются с живой памятью
                  ├─ carrier        FTSTicker → работа на игровом потоке
                  ├─ resolver       обход GUObjectArray срезами, на игровом потоке
                  ├─ content        поколения контента: publish / acquire / revoke
                  ├─ bridge         C-ABI, MbRoot 40 байт, таблицы по capability
                  ├─ input          подкласс оконной процедуры игры → клавиатура
                  ├─ console UI     overlay-окно поверх клиентской области
                  └─ CoreCLR
                        Misery.ModHost.dll   ← загружает моды, владеет их ALC
                        Misery.ModAPI.dll    ← публичные контракты, версия 0.5.0
                        Mods/<ModName>/
                              mod.json       манифест
                              Code/*.dll     сборка мода
                              Content/*.utoc контент мода
```

Через ABI не ходят делегаты и managed-типы: обработчики живут в трамплине на
стороне хоста, а нативная сторона зовёт их по числовому виду диспатча. Это
то, что позволяет выгрузить мод и собрать его `AssemblyLoadContext`.

Ключевые правила, которые видно в коде:

* **Только игровой поток.** Всё, что трогает состояние движка, идёт через
  диспетчер; вызов не с того потока — структурированная ошибка, а не UB.
* **Поколения контента.** Мир заменяется — старое поколение отзывается, и
  указатели на него перестают разрешаться. Мод об этом не думает: его
  объявления переносятся в новое поколение, и он получает `content_ready`.
* **Revoke-before-release.** Выгрузка мода сначала отзывает всё, чем он владеет,
  и только потом отпускает слоты.

## 4. Как выглядит мод

Папка. Манифест перечисляет, что в ней лежит; класс объявляет, какие
capability ему нужны; фреймворк выдаёт грант и не даёт больше.

```
Mods/ReferenceMod/
  mod.json          {"manifest_version": 1, "mod_id": "refmod",
                     "name": "MBPL Reference Mod", "version": "1.0.0",
                     "framework_api": "^0.5.0",
                     "code": ["RefMod.dll"], "content": ["Mod_refmod_P"]}
  Code/RefMod.dll
  Content/Mod_refmod_P.{pak,utoc,ucas}
```

```csharp
[ModCapabilities(Capabilities.Log, Capabilities.Items,
                 Capabilities.Events, Capabilities.Console,
                 FrameworkApi = "^0.5.0")]
public sealed class ReferenceMod : IMod
{
    public void OnLoad(IModContext context)
    {
        _item = context.Items.Register(new ItemDeclaration(
            localId: "sample", displayName: "Reference Sample", /* ... */)
            { WorldClass = "/Game/Mods/refmod/Blueprints/BP_WorldItem.BP_WorldItem_C" },
            out string rowName);

        // Мир может ещё не существовать: OnLoad выполняется в главном меню.
        context.Events.Subscribe(FrameworkEvents.ContentReady, OnContentReady);
    }

    public void OnUnload() => _item?.Dispose();
}
```

Ни одного движкового понятия в этом коде нет: ни `UObject`, ни `FName`, ни
`ProcessEvent`, ни адреса. Путь к классу — это **данные**, ровно как путь к мешу.
Полный пример — `reference/refmod/Code/RefMod.cs`.

## 5. Чего пока нет

Отдельный раздел, потому что список ограничений — часть описания платформы, а не
приложение к нему.

| Чего нет | Готовность | Комментарий |
|---|---|---|
| Мультиплеер | **PLANNED** | Ничего из сетевой части не исследовано и не построено; все наблюдения сделаны в standalone. Stage 9 |
| Широкий gameplay-SDK | **PLANNED** | Игрок, мир, бой, ИИ, погода, крафт: подсистемы описаны в `research/systems/` неравномерно, публичного API нет. Stage 10 |
| Привязка клавиш модом | **NOT IMPLEMENTED** | Доставка клавиатуры работает и её потребляет консоль, но мод не может повесить действие на клавишу. `misery:input` сообщает это прямо: `mod_bindings: false` |
| UI-фреймворк для модов | **NOT IMPLEMENTED** | Консоль — это консоль, а не система виджетов |
| Публичный Mod Kit для сторонних авторов | **NOT IMPLEMENTED** | Контент мода собирается инструментами репозитория на машине разработчика |
| Публичный установщик / release | **NOT IMPLEMENTED** | Отложено до после Stage 10, см. дорожную карту |

**Работает, но с оговоркой:**

* **Консоль не видна в exclusive fullscreen.** Overlay — это отдельное окно, а
  поверх exclusive-swapchain снаружи не рисует ничего. В borderless и оконном
  режиме проверено; в exclusive — консоль продолжает работать и остаётся
  невидимой. Ограничение механизма, названное заранее, а не обнаруженное
  пользователем.
* **Blueprint-подкласс доказан для одного родителя.** См. NARROW выше.
* **Одна сборка игры.** Утверждения о переносимости между версиями остаются
  гипотезами до появления второй сборки; профиль привязок для того и
  fail-closed.
* **Поведение при co-op не наблюдалось вообще** — ни разу, ни в одном прогоне.

| Файл | Что это |

| `research/RESEARCH_LOG.md` | Append-only журнал: вопрос → метод → evidence → вывод → confidence. |

| `research/decisions.md` | Журнал решений (D-01..D-nn). |

**Историческое остаётся историческим.** `research/evidence/**`, старые
acceptance-отчёты, preregistration-документы и журналы **не переписываются**,
чтобы звучать современно: они фиксируют то, что было правдой в момент записи, и
в этом их единственная ценность. Если исторический документ можно принять за
описание текущего состояния — на него ставится баннер со ссылкой сюда, а не
правится его содержание.

### Структура

```
runtime/          нативная часть: bootstrap-прокси и MiseryRuntime
managed/          Misery.ModAPI (публичные контракты) и Misery.ModHost
reference/refmod/ reference-мод: только публичный API, ничего привилегированного
tools/            modplatform, modkit, discovery, fingerprint, inventory, kb
pyghidra_scripts/ скрипты для Ghidra headless
tests/            автотесты платформы и инструментов
docs/             архитектурные документы, feasibility-оценки, toolchain
research/         knowledge base: журнал, решения, системы, evidence, инструменты
workspace/        НЕ в git: сборки, копии бинарников, крупные дампы
```

### Три правила, которые нарушаются чаще всего

1. **Вывод, который есть только в чате, не существует.** Инвариант:
   `question → method → evidence → finding → confidence → persistent artifact`.
2. **Всегда носить `oracle` и `confidence`.** Словарь `oracle` закрыт девятью
   значениями (`plan.md` §10.5); значение вне списка валидатор отклоняет.
   Каждый источник доказывает свой класс утверждений и не доказывает остальные.
3. **Догадка не повышается в звании молча.** `HYPOTHESIS` становится `INFERRED`
   или `OBSERVED` только вместе с новым evidence и новой записью в журнале.
   Неизвестное пишется как `UNKNOWN`, а не как правдоподобная формулировка.

### Гейт CI

Значок вверху живой: он показывает цвет последнего прогона на `main`, и цвет
здесь намеренно **не продублирован словами** — типизированное заявление о
статусе во втором файле протухает молча. Красный означает, что наши собственные
документы ещё не удовлетворяют нашим же правилам доказательности
(`tools/kb/validate.py`), а не что платформа сломана. Актуальные числа живут
ровно в одном месте — сгенерированный блок `docs/toolchain.md` §15.1.

### Установка окружения разработки

Полная процедура, версии и известные несовместимости — в `docs/toolchain.md`.
Здесь не дублируется, чтобы не разъехалось. Минимум: Ghidra только на JDK 21
(JDK 25 падает), Python-окружение — отдельный venv, установка зависимостей в
два шага (см. header `requirements.txt`), MSVC 14.38 для нативной части.

Ещё раз, потому что это главное недоразумение, которое здесь возможно:
**поставляемого пакета нет.** Всё вышеописанное собирается из исходников и
устанавливается в собственную копию игры разработчика.
