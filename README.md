# MISERY Modding Framework

[![CI](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml)

**Коротко.** Исследование сборки игры MISERY (Unreal Engine 5.4.4) ради будущего modding
framework. Содержимое репозитория на сегодня — знание о сборке и методология его добычи; ни мода,
ни SDK, ни загрузчика здесь нет. Разбор — в разделах ниже.

**Фаза.** **Phase 1 — Research.** Только исследование: production loader, SDK и любой код, пишущий
в память запущенной игры, в этой фазе намеренно не создаются (подробнее — ниже). Текущий milestone
и что в нём закрыто — раздел «Где мы сейчас» ниже; exit criteria — в `plan.md` §18.

**Состояние гейта — значок выше. Он живой: показывает цвет последнего прогона CI на `main`, а не
запись о нём.** Здесь цвет намеренно **не продублирован словами**: типизированное заявление о статусе
во втором файле — это ровно тот дефект, из-за которого блок чисел в `docs/toolchain.md` дважды
протухал. Числа и статус живут в одном сгенерированном месте, всё остальное на него ссылается.

Красный означает, что **наши собственные документы ещё не удовлетворяют нашим же правилам
доказательности**: валидатор базы знаний (`tools/kb/validate.py`) находит записи, где факт записан
без обязательного oracle, с запрещённой оценкой или смешивает измерение с его трактовкой под одной
оценкой. Это **самоназначенный** гейт: его правила мы написали себе сами (`plan.md` §10,
`research/evidence-model.md`), и падает он по нашим документам, а не по коду игры и не по
инструментам.

Чего красный цвет **не** означает: что исследование сломано, что факты в репозитории недостоверны
или что сборка не проанализирована. Гейт, который краснеет на собственных документах, — это гейт,
который работает. Зелёным он станет тогда, когда каждая запись будет соответствовать правилам, а не
тогда, когда правила ослабят: ослаблять их ради зелёного прогона запрещено прямо в шапке
`tests/test_validator_live.py`.

Актуальные числа — нарушений, записей, провалившихся тестов — живут в репозитории **ровно в одном
месте**: сгенерированный блок в `docs/toolchain.md` §15.1, с датой снятия и командой обновления
(`.github/scripts/kb_status.py`). Здесь они сознательно не дублируются: значок жив, а число
пришлось бы обновлять руками — так и появляются устаревшие статусы, выданные за текущие.

## Что это

Исследовательский репозиторий проекта по созданию **modding framework для игры MISERY**
(Unreal Engine 5.4.4, Steam AppID 2119830).

Ключевое архитектурное намерение: framework строится на **собственном фундаменте и не зависит от
UE4SS** — ни как runtime-зависимость, ни как встроенный в продукт код (ограничение C-04 в `AGENTS.md`).
UE4SS допустим ровно в двух ролях: источник публичной документации по структурам Unreal Engine и
независимая точка сверки гипотез. Ничего больше.

## В какой фазе мы находимся

**Phase 1 — Research.** Только исследование.

В этой фазе намеренно **не** создаются:

* production loader,
* SDK и generated bindings,
* какой-либо код, который пишет в память запущенной игры.

Результат Phase 1 — знание, зафиксированное в файлах, и обоснованный вердикт о том, что вообще
возможно (`docs/phase1-report.md`). Не работающий мод. Отрицательный вердикт по ключевому гейту
(E-3b, §14A.7 плана) — это **главный результат**, а не провал; смягчать такую формулировку запрещено.

## Жёсткие правила до первого действия

1. **Установка игры `D:\Games\Steam\steamapps\common\MISERY` — исключительно read-only research
   target** (решение D-01, ПРИНЯТО). В неё **ничего не пишется**: ни `>`, ни `>>`, ни `Set-Content`,
   ни `Move-Item`, ни `Remove-Item`, ни `attrib`. Чтение — можно и нужно.
2. **Ни один инструмент не принимает путь внутри установки игры как output-путь.** Всё, что нужно
   открыть инструментом, способным писать (Ghidra, любой патчер, любой распаковщик), сначала
   **копируется в `workspace/bin/`**. Оригинал открывается только потоковым чтением — для хэширования
   и парсинга.
3. **Верификация вместо надежды.** `tools/inventory/verify_install.py` сравнивает состояние установки
   с `install-inventory.json` (путь + размер + mtime + sha256) и печатает diff. Baseline — 53 файла.
   Запускать после каждого milestone, до и после любой сессии с запущенной игрой.
4. **Ключ шифрования основного контейнера не извлекается, контейнер не расшифровывается** (D-02).
   Разрешённые источники — см. D-11 и `docs/research-vs-product.md` §2 (`P-1..P-9`); список больше не
   закрыт четырьмя пунктами. Запрет на ключ и на расшифровку основного контейнера — в силе дословно.
5. **Второй `MISERY.exe` (282 МБ) — read-only oracle** (D-04). Называть его «Development build» без
   доказательства запрещено: это HYPOTHESIS. Он никогда не является target для bindings.
6. **Догадка не называется фактом** (C-07). Любой факт несёт `evidence level`, `confidence` и `oracle`.

## Настройка окружения

Полная процедура, версии, sha256 архивов и известные несовместимости — в **`docs/toolchain.md`**.
Здесь она сознательно не дублируется, чтобы не разъехалась.

Минимум, что нужно знать заранее:

* Ghidra запускается только с JDK 21 (путь прописан в `support/launch.properties`). **JDK 25 не

  зависимостей — **два шага**, порядок важен: см. header в `requirements.txt`.

## Как не сломать исследование

Три правила, которые нарушаются чаще всего и стоят дороже всего.

1. **Вывод, который есть только в чате, не существует.** Инвариант: `question → method → evidence →
   finding → confidence → persistent artifact → next question`. Пока вывод не записан файлом в
   `research/`, его нет. Записывать сразу, а не «в конце сессии».
2. **Всегда носить `oracle` и `confidence`.** У каждого факта — из какого источника он получен и
   насколько мы в нём уверены. Словарь `oracle` **закрыт девятью значениями** (`plan.md` §10.5,
   правка v2.1):

   | Значение | Что это |
   |---|---|
   | `filesystem` | прямое read-only наблюдение файлового дерева |
   | `steam-metadata` | служебные данные Steam (`appmanifest_*.acf`, `libraryfolders.vdf`, манифесты депотов) |
   | `vcs-history` | история нашего собственного репозитория |
   | `global-ucas` | имена native / script-объектов из глобального контейнера |
   | `asset-registry` | packages и assets, полученные runtime-чтением AssetRegistry |
   | `runtime-reflection` | `UClass`/`UFunction`/`FProperty` в том виде, в каком их видит запущенный движок |
   | `binary-analysis` | native-реализация, восстановленная из кода (Ghidra) |
   | `container-metadata` | наши парсеры `.utoc`/`.pak` |
   | `external-doc` | публичная документация и исходники UE, проверенные open-source инструменты |

   Первые три — не «служебные»: `filesystem`, `steam-metadata` и `vcs-history` добавлены правкой
   v2.1 именно потому, что ни одно из остальных шести не покрывало **самый частый** способ добыть
   факт в M0 — чтение файлового дерева. Без них около пятидесяти строк `research/repo-audit.md`
   были незаписываемы по собственному словарю проекта. Значение вне этих девяти валидатор
   отклоняет (`EV-04`), поэтому список здесь приведён целиком, а не «основными» позициями.

   Каждый источник доказывает **свой** класс утверждений и не доказывает остальные — матрица в
   `research/evidence-model.md` §5. Имя в `global.ucas` **не** доказывает существование ассета из
   `/Game`, и тем более не доказывает его структуру.
3. **Догадка не повышается в звании молча.** `HYPOTHESIS` становится `INFERRED` или `OBSERVED` только
   вместе с новым evidence и новой записью в журнале. Если что-то неизвестно — пишется `UNKNOWN`,
   а не правдоподобная формулировка. Смена уровня без evidence — это тот самый способ, которым
   исследование начинает лгать себе.
