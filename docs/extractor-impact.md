# Misery Research Extractor — impact analysis относительно `plan.md`

**Дата:** 2026-08-23. **Статус:** анализ влияния, не решение. Решения принимает владелец.
**Повод:** расширение цели Phase 1 — помимо reverse engineering, строить собственный
MISERY-specific extractor / semantic reconstructor для UE 5.4.4, дающий семантический образ игры,
достаточный для будущих SDK, bindings, Mod Kit и content-модов.

**Главный вывод сразу:** это **не новый проект**. Из тринадцати компонентов заявленного extractor'а
**восемь уже существуют в плане как методы с ID**, и требуется не новая методология, а (а) слой
данных, который их результаты связывает, и (б) **одно переупорядочивание milestone'ов**, которое
снимает с критического пути целый runtime-этап. Ниже — что именно меняется, чего не меняется, и
почему переупорядочивание обязано случиться независимо от extractor'а.

---

## 1. Самое важное следствие: RF-01 не нуждается в M3

`plan.md` строка 473 определяет метод **RF-01** как «Разбор **незашифрованного** `global.ucas`
(script objects + global FName pool)». Слово «незашифрованного» стоит в плане с самого начала —
предсказание оказалось верным. Строка 1776 назначает RF-01 в **M3 «Reflection access via ERI»**,
то есть за External Read-Only Inspector, за ответ по гейту Q-8 и за всю оснастку наблюдения
запущенного процесса.

Измерено 2026-08-23: `global.utoc` — 623 байта, `ContainerFlags = 0x00`, **не зашифрован**;
`global.ucas` — 2 269 168 байт, энтропия Шеннона 6,653 бита на байт (AES дал бы ≈7,99), 9,3 %
нулевых байт, 394 вхождения `/Script/`, 6515 вхождений `Default__`.

**Значит RF-01 — статическая работа, и в M3 ему делать нечего.** Он не требует процесса, ключа,
инструментирования и разрешения по §8.4. Это не смягчение правила и не обход гейта: гейт Q-8
охраняет *наблюдение запущенного процесса*, а чтение файла на диске к нему не относится.

Что это освобождает — по цепочке из самого плана:

| Метод | Что даёт | Раньше ждал | Теперь ждёт |
|---|---|---|---|
| RF-01 | имена всех `/Script/<Module>`, классов, функций | M3 (ERI, Q-8, §8.4) | ничего |
| RF-02 | разделение «движковое vs игровое» | RF-01 | RF-01 |
| RF-03 | кандидатные адреса `FName`-литералов в образе | RF-01 | RF-01 |

RF-02 — это ровно то, чего у проекта нет ни из одного другого источника: S-10 нашёл **0 классов
игры** в RTTI, а `global.ucas` — первая поверхность, которая игровой код вообще называет.

**Предлагаемая правка (минимальная):** перенести RF-01, RF-02, RF-03 из M3 в **M2s**, оставив в M3
двустороннюю валидацию «статика ↔ runtime» и первый проход CR-01. M3 от этого не пустеет — он
меняет роль с «получить карту» на «подтвердить карту в рантайме», а это честнее: карта из
контейнера и карта из живого процесса — два разных измерительных акта, и их расхождение само по
себе является находкой.

**Чего этот вывод НЕ даёт.** Нельзя заранее утверждать, что `global.ucas` — полноценная reflection
map. Требование владельца: «сначала определить точную информационную границу этого источника». По
раскладке UE script-object registry ожидаемо содержит **имена и отношения outer**, но не
обязательно типы свойств, их смещения и полные сигнатуры функций. Пока границу не измерили,
корректная формулировка — «карта имён и отношений», а не «reflection map». Это записано как
обязательный первый результат RF-01, а не как оговорка в примечании.

Восемь из тринадцати покрыты. Пять пробелов, и они не методологические, а **сборочные**: нет слоя,
который связывает уже добываемые факты в один граф.

**Про MiseryDB.** Требование владельца — не изобретать формат ради имени. `plan.md` §9.2 уже
задаёт `research/reflection/<build_key>/` с `classes.jsonl`, `functions.jsonl`,
`properties.jsonl`, `enums.jsonl`, `relations.jsonl`. Это и есть MiseryDB. Не хватает файлов
`imports.jsonl`, `exports.jsonl`, `dependencies.jsonl`, `defaults.jsonl` и — позже —
`bytecode.jsonl`; плюс каждой записи нужны поля `evidence_level`, `confidence`, `oracle`,
`build_key`, которых схема требует и так. Новый формат не нужен. Нужны новые файлы в существующей
раскладке и одна схема на запись сущности.

## 3. Единица семантической модели

Владелец перечислил поля желаемой сущности. Проблема не в перечне, а в том, что **разные поля
приходят из источников разной силы**, и запись, склеивающая их под одной оценкой, нарушает §10.3
(«смешанные утверждения обязаны разделяться»). Пример из требования — `BP_AK74_C` с родителем
`/Script/MISERY.MiseryWeapon`, свойствами `Damage`/`AmmoType`/`MagazineSize` и функциями
`Fire`/`Reload` — на практике собирается минимум из четырёх источников.

Поэтому запись сущности обязана быть **композитной с покомпонентной градацией**: одно поле — один
источник — одна оценка. Не одна оценка на сущность.

| Поле | Источник | Оракул | Ожидаемая сила |
|---|---|---|---|
| canonical name, outer | RF-01 | `global-ucas` | сильная |
| native / script / blueprint origin | RF-01 + RF-02 | `global-ucas` + `external-doc` | средняя |
| parent, interfaces | cooked package или RF-01 | `container-metadata` / `global-ucas` | зависит |
| properties, типы | cooked package, RF-08 | `container-metadata` / `binary-analysis` | средняя |
| смещения свойств | **никогда из статики напрямую** — см. CK-04 | — | UNKNOWN до ответа |
| function signatures | cooked package + RF-01 | смешанный | средняя |
| CDO / default values | cooked package (export data) | `container-metadata` | средняя |
| imports / exports / dependencies | cooked package summary | `container-metadata` | сильная при доступе |
| asset references, soft paths | package + AssetRegistry | `asset-registry` | средняя |
| Blueprint bytecode | export data | `container-metadata` | неизвестна до §5 |
| native implementation candidate | RF-04..RF-09, S-06/S-07 | `binary-analysis` | **всегда HYPOTHESIS** |
| replication / network flags | cooked package flags | `container-metadata` | средняя |

Два правила, которые надо зафиксировать до первой строки кода, потому что нарушить их дешевле, чем
потом вычистить:

1. **Имя в `global.ucas` не доказывает существование `/Game`-ассета.** `plan.md` (правка v2 п. 13)
   это уже запрещает. Extractor обязан держать `/Script/*` и `/Game/*` в **разных множествах** и
   никогда не выводить второе из первого.
2. **Ребро «native implementation candidate» — гипотеза, а не факт.** Сопоставление отраженной
   функции с адресом в образе — интерпретация; ей полагается HYPOTHESIS и сигнатура, по которой её
   можно перепроверить на новой сборке (S-06/S-07 уже для этого построены).

## 4. Минимальная архитектура

Не одна программа, а конвейер из инструментов, каждый из которых пишет JSONL и проверяем отдельно.
Это следует из уже действующих правил: только стандартная библиотека, read-only относительно игры,
детерминированность, разделение измерения и интерпретации.

```
tools/reflection/global_ucas.py     RF-01  →  names.jsonl, script_objects.jsonl
tools/reflection/engine_split.py    RF-02  →  classifies /Script/* engine vs game
tools/content/package_reader.py     новый  →  summary, imports, exports, deps
tools/content/export_decoder.py     новый  →  CDO/default values, DataAsset/DataTable rows
tools/content/kismet_decoder.py     новый, ОТЛОЖЕН до §5 →  bytecode.jsonl
tools/correlate/native_link.py      RF-03/09 + S-06/S-07  →  candidate edges, HYPOTHESIS
tools/kb/build_semantic.py          новый  →  сводит JSONL в research/reflection/<build_key>/
tools/kb/semantic_diff.py           новый  →  diff двух build_key
```

Три свойства архитектуры, обязательные с самого начала:

* **Композиция, а не монолит.** Каждый слой читает артефакты предыдущего, а не вызывает его в
  памяти. Иначе неверный разбор одного слоя тихо отравляет всё, а обнаружить это будет нечем.
* **Ключ сущности не зависит от build.** Требование владельца — не привязывать архитектуру к
  `24826585`. Значит канонический ключ — полный путь объекта (`/Script/MISERY.MiseryWeapon`), а
  `build_key` — поле записи, не часть ключа. Иначе diff двух сборок невозможен в принципе.
* **Структурная самопроверка в каждом парсере.** Разбор контейнера обязан сообщать, **замощает** ли
  он вход точно, без дыр и перекрытий. Именно эта проверка отличила верный разбор `.pak` от
  угаданного: первая попытка декодировала битовое поле по маскам из памяти и выдала уверенно
  неверный ответ, а замощение 53 088 из 53 088 байт подтвердило верный.

## 5. Blueprint bytecode: зависимая задача, и её надо мерить, а не начинать

Требование владельца: начинать декомпилятор **только после подтверждения**, какой bytecode реально
присутствует и насколько он полезен. Это правильный порядок, и вот почему он важен именно здесь.

Kismet bytecode живёт в **export data** пакета, то есть внутри `MISERY-Windows.ucas`, который
зашифрован. Значит вопрос «сколько Blueprint-логики осталось в сборке» сегодня не имеет
измерительного ответа из offline-разбора — и признать это надо прямо, а не строить декодер под
данные, которых пока не видно.

Порядок, который из этого следует:

1. Определить на **собственном** куке UE 5.4.4, где именно bytecode лежит и в каком виде — это
   измеримо немедленно и не требует ничего от игры.
2. Определить, есть ли доступная исследовательская поверхность к export data игры.
3. Только тогда — декодер опкодов `EX_*`, базовые блоки, CFG, псевдокод.

Уровень цели зафиксировать сразу, чтобы не разрастался: псевдокод вида «`if DistanceToPlayer <
AggroRange: UpdatePerception()`». Не граф редактора, не позиции узлов, не комментарии автора, не
имена вырезанных локальных переменных — этих данных в cooked-сборке нет, и §13 требования это прямо
исключает.

## 7. Правки в `plan.md`, которые из этого следуют

Строго локальные. Ни одна не меняет методологию, модель доказательности или нумерацию существующих
разделов.

1. **Строка 1776 (M3) и 1775 (M2s):** перенести RF-01, RF-02, RF-03 в M2s; в M3 оставить
   двустороннюю валидацию статика↔runtime и первый проход CR-01. Обоснование — §1 этого документа.
2. **Новый §9.5 «MiseryDB — семантическая модель»:** единица сущности, покомпонентная градация,
   новые файлы в существующей раскладке §9.2, правило «ключ не зависит от build».
3. **Новый §5A «Extractor: составные методы»** — идентификаторы `EX-01..EX-08` для слоёв конвейера
   §4, чтобы на них можно было ссылаться из журнала и из `unknowns.md`.
4. **§14A:** добавить, что генератор stubs потребляет `research/reflection/<build_key>/`, а не
   собственный формат; гейт E-3b не меняется.
5. **§16:** расширить «detect a content-only patch» до семантического diff (§12 требования).
6. **§13 требования → новый пункт в §16 рисков:** зафиксировать как *не*-цель восстановление
   комментариев, структуры файлов, позиций узлов и вырезанных имён. Это защита от разрастания
   цели, и её отсутствие само является риском.

Нумерация `§5A`, `§9.4`, как и уже применённые `§14A` и `§14.7a`, выбрана чтобы **не сдвигать**
существующие разделы: на них ссылаются журнал, реестры и решения.

## 8. Что этот трек не меняет

* Модель доказательности §10 — без изменений. Extractor обязан ей подчиняться, а не наоборот.
* Гейт **E-3b** остаётся главным гейтом проекта. Полнота семантической модели не заменяет
  подтверждения, что MISERY примет пакет с Blueprint от native-родителя.
* Граница research / production — без изменений и в силе: extractor может быть публичным,
  расшифрованные контейнеры, оригинальные ассеты и ключи — нет, и готовый framework обязан
  работать с обычной Steam-установкой.
* **D-02 в части «не извлекать ключ и не расшифровывать основной контейнер» продолжает
  действовать** до отдельного решения владельца. Изменилось другое: встреча с зашифрованным
  payload'ом больше не закрывает content track — ищется другая поверхность к тому же знанию.
* «Development build» для второго `MISERY.exe` остаётся HYPOTHESIS 0.65 (D-04).

## 9. Честные риски именно этого трека

| Риск | Почему реален | Что делаем |
|---|---|---|
| Ложное восстановление выглядит как знание | граф из имён соблазняет достроить связи, которых в данных нет | UNKNOWN обязателен; `/Script/*` и `/Game/*` — разные множества; ребро native — HYPOTHESIS |
| Информационная граница `global.ucas` окажется узкой | script-object registry может нести имена без типов и смещений | измерить границу **первым** результатом RF-01, до любых обещаний |
| Собственный кук ≠ кук игры | наши настройки не обязаны совпадать с их | сравнение только по признакам, читаемым у игры; расхождение — находка, не шум |
| Extractor разрастётся в самоцель | «восстановить исходники» — бесконечная задача | §13 требования как норма: цель — semantic equivalence для моддинга |
| Архитектура прилипнет к одной сборке | самое дешёвое решение — вписать `build_key` в ключ | ключ = путь объекта; `build_key` = поле |
| Bytecode-декодер начнут до данных | самая интересная часть, поэтому притягивает | порядок §5 обязателен: сначала измерить, что есть |
