# Toolchain

Задача **T-01** (`plan.md` §17.4). Источник требований — `plan.md` §17 (§17.1, §17.1a, §17.2, §17.3, §17.6).

* **Назначение файла:** это документ, по которому окружение исследования восстанавливается с нуля на чистой машине. Всё, что нужно знать для повторной установки, включая **наши правки в сторонних установках**, находится здесь.
* **Дата верификации содержимого:** 2026-08-22. Все версии, пути, размеры и контрольные суммы в этом файле перепроверены запуском/чтением файловой системы в день записи, кроме явно помеченных случаев.
* **Ответственный риск:** RISK-14 (toolchain живёт вне репозитория, версии могут разойтись с документацией). Единственная защита — сверка с этим файлом при любой переустановке.

## 0. Как этим пользоваться

1. Если вы восстанавливаете окружение — идите в §8 «Recipe». Прежде чем что-либо запускать — §3.1: канонический интерпретатор Python ровно один.
2. Если вы переустановили или обновили Ghidra — обязательно прочитайте §5 (иначе Ghidra подхватит Java 8 с PATH и не запустится) и §7.1 (проверка версии JDK).
3. Если вы собираетесь применить сторонний инструмент к контейнерам игры — сначала §6.2 (C-12) и §14 (D-11, преемник D-02) и `docs/research-vs-product.md`.
4. Если что-то в этом файле расходится с фактическим состоянием машины — это находка, а не опечатка: см. §2 и `research/decisions.md`.

## 1. Легенда evidence level

Каждое нетривиальное утверждение помечено по `plan.md` §10.1 (сами уровни) и §10.5 (допустимые значения `oracle`):

| Метка | Значение |
|---|---|
| `OBSERVED` | проверено запуском или прямым чтением файловой системы, с указанием чем именно |
| `INFERRED` | выведено из наблюдений, но сам вывод не проверялся напрямую |
| `HYPOTHESIS` | правдоподобное объяснение, доказательств нет |
| `UNKNOWN` | не выяснено; так и записано, догадка не подставляется |

Применимые `oracle` для утверждений этого документа — ровно два значения из девяти, перечисленных в `plan.md` §10.5: `external-doc` (документация, релизы и исходники сторонних проектов, а также поведение сторонних инструментов) и `filesystem` (прямое read-only чтение файлового дерева: наличие путей, версии из файлов вроде `Build.version` и `application.properties`, размеры, sha256, вывод `--version`). Формулировка «локальные наблюдения окружения», стоявшая здесь раньше, значением словаря не является и заменена на `filesystem`.

**Ни одно утверждение из этого файла не является утверждением о сборке игры.** Поэтому потолок «`external-doc` ≤ 0.7» (§6.2 п.1), сформулированный применительно к выводам об **этой сборке**, к утверждениям об инструментах здесь не применяется — и ни одна цифра отсюда не переносится на MISERY.

## 2. Расхождения с `plan.md` §17.1, обнаруженные при верификации 2026-08-22

> Эти два пункта — самое важное в файле. Оба меняют оценку выполнимости целых разделов плана. Ни один из них не был известен на момент написания §17.1.

### 2.1 MSVC toolset фактически ОТСУТСТВУЕТ (было записано как «уже есть»)

`plan.md` §17.1 и §17.2 утверждают, что MSVC (VS 2022, `VC.Tools.x86.x64`) присутствует по пути `D:\Program Files\VisualStudio` и что для сборки достаточно вызвать `vcvars64.bat`. Фактически:

| Проверка | Результат |
|---|---|
| `vswhere.exe -all -products *` | одна запись: `Visual Studio Community 2026`, `installationVersion 18.5.11709.299`, `installationPath D:\Program Files\VisualStudio`, **`isComplete: false`**, **`isLaunchable: false`**, `state: 14`, `installDate 2026-04-14` |
| `Test-Path "D:\Program Files\VisualStudio"` | **False** — каталога на диске нет |
| `ls "/d/Program Files/"` | каталога `VisualStudio` в листинге нет |
| `C:\Program Files (x86)\Microsoft Visual Studio\2019` и `\2022` | существуют, но **пусты** |
| `find … -name vcvars64.bat` | **ничего не найдено** |
| `find … -name cl.exe` | **ничего не найдено** |

**Вывод:** записи установщика VS остались, самого toolset нет. `cl.exe`, `vcvars64.bat`, VC-runtime-заголовки недоступны. Evidence level `OBSERVED`, confidence **0.97** (остаток покрывает возможность MSVC в непросмотренном нестандартном пути; поиск шёл по всем стандартным корням VS и по обоим `Program Files`).

**Независимое подтверждение из другого источника.** `plan.md` §17.1a фиксирует, что при попытке установить `jpype1==1.5.2` pip ушёл в сборку из исходников и **упал на отсутствии MSVC в окружении**. Это ровно то, что предсказывает наблюдение выше. Два независимых наблюдения согласуются.

**Последствия, которые надо занести в план и в `research/unknowns.md`:**

* §14A (mod-kit модуль редактора, native-наследование) требует сборки UE C++ модуля. UE на Windows требует **именно MSVC**, MinGW не подходит. Пока MSVC не установлен, §14A **заблокирован по инструментарию**, а не только по знанию.
* Любое расширение Python на C (в том числе сборка колёс из исходников) невозможно. Поэтому политика §7.2 «выбирать версии с готовыми колёсами» — не удобство, а жёсткое требование.
* Вариант ERI/IPP на C++ (§17.2) сейчас нереализуем; вариант на Rust — реализуем (см. §3).
* MinGW-w64 GCC на машине есть (§14.5), но он **не** замена MSVC ни для UE, ни для CPython-ABI.

Установленный движок сообщает **ровно те же** три значения. Это не «примерно та же версия движка», это **побитово тот же promoted build**, чего требует мера против RISK-15 («использовать ровно версию движка сборки (5.4.4)»).

**Что из этого НЕ следует** (важно, чтобы не превратить находку в догадку):

* Не следует, что cook в этом движке даст пакет, который данная сборка примет и прочитает верно. Это ровно RISK-15, и он остаётся открытым. Совпадение CL **улучшает** шансы, но не является доказательством.
* Не следует, что Tier C доступен «сразу». Tier C по §14.7 требует ещё и рабочего проекта, а для §14A — вдобавок MSVC, которого нет (§2.1). Для **BP-only** проекта MSVC не нужен — это отдельный, более дешёвый путь, который стоит проверить первым.
* Не следует, что установка «наша». Движок поставил владелец машины до начала проекта; никаких наших правок в нём нет и вносить их без отдельного решения нельзя.
* Не следует ничего о содержимом контейнеров игры. D-02 в силе безусловно.

**Что делать:** это вход для переоценки D-06, RISK-04 и §14.7 (триггер установки UE фактически уже удовлетворён без затрат диска). Соответствующая запись — в `research/decisions.md` и `research/unknowns.md`, не здесь; этот файл только фиксирует наличие инструмента.

### 3.1 Канонический интерпретатор Python — ровно один

> **Тесты и валидация базы знаний запускаются `D:\Tools\venv-research\Scripts\python.exe` и никаким другим интерпретатором.**

`C:\Python314\python.exe` — **только база**, из которой создаётся venv (`requirements.txt`, шаг 1 канонической последовательности). Запускать им `pytest` или `tools/kb/validate.py` запрещено: это машинный интерпретатор, состав пакетов в нём не описан ни `requirements.txt`, ни этим файлом, поэтому зелёный прогон под ним ничего не говорит о свежем клоне.

**Почему это выделено в отдельный пункт (находка MAJOR-6, 2026-08-22).** До 2026-08-22 в venv-research не было ни `jsonschema`, ни `pytest`. Последствия были двумя разными видами молчаливой лжи:

* `tools/kb/validate.py` при неудачном импорте `jsonschema` **не падает**, а переключается на встроенный минимальный валидатор, который игнорирует `format` и `propertyNames`, и завершается с кодом 0. То есть exit criterion K-03 «валидация проходит чисто» выполнялся, ничего фактически не проверяя. Признак настоящего бэкенда — строка баннера `schema backend: jsonschema (full JSON Schema validation)`; строка `BUILT-IN MINIMAL VALIDATOR` означает, что результат валидации **не имеет силы**.
* `tests/` под каноническим интерпретатором не запускались вообще — только под системным `C:\Python314`, то есть по случайности состава чужого окружения. На 2026-08-22 это два модуля, **1423 строки** (`test_kb.py` 832, `test_inventory.py` 591 — измерено подсчётом строк).

Оба пакета установлены и проверены 2026-08-22 (§9.4). Пины и точные команды воспроизведения — **в `requirements.txt`**; здесь они сознательно не дублируются, чтобы два документа не могли снова разойтись (именно расхождение `requirements.txt` ↔ §9.4 и было находкой). Этот файл отвечает за «какой интерпретатор канонический и чем он проверяется» (§15), `requirements.txt` — за «какие версии и какими командами ставятся».

### 3.2 Машинно-специфичные пути в этом файле (C-13)

Репозиторий публичный, поэтому пути внутри профиля пользователя записываются переменными окружения (`%USERPROFILE%`, `%APPDATA%`, `%LOCALAPPDATA%`), а не буквально: буквальный путь раскрывает имя учётной записи владельца машины. Правка 2026-08-22: строка Rust/cargo в Таблице A содержала буквальный путь профиля и заменена на `%USERPROFILE%\.cargo\bin\`. Значение при этом не потеряно — rustup ставит cargo именно туда, и раскрытие переменной даёт тот же каталог на любой машине.

Пути на `D:` и в `C:\Program Files` буквальными остаются сознательно: они не содержат имени пользователя, а их точность — смысл этого документа.

### 4.1 Оговорка про URL

Точные URL конкретных asset'ов релизов **сознательно не выписаны как прямые ссылки на файл**: имена тегов и путей загрузки — деталь, которая проверяется на странице релиза, а не восстанавливается по памяти. При повторной установке действуйте так:

1. откройте страницу релизов проекта (URL выше — он стабилен);
2. найдите релиз с **точно той версией**, что в Таблице A;
3. возьмите asset с **точно тем именем файла**, что в Таблице B;
4. сверьте **размер в байтах** и **sha256** с Таблицей B. Совпадение по обоим полям — и есть подтверждение, что вы взяли ровно тот же артефакт.

Если sha256 не совпал — **остановитесь**. Это либо другой релиз, либо повреждённая загрузка, либо подмена. Не «наверное так и должно быть».

## 5. Наши правки в сторонних установках

> Правило: любая правка, внесённая нами в чужой дистрибутив, обязана быть перечислена здесь. Иначе при переустановке она теряется молча, и окружение перестаёт работать без понятной причины.

**На 2026-08-22 такая правка ровно одна.**

### 5.1 Ghidra: `support/launch.properties` → `JAVA_HOME_OVERRIDE`

| Поле | Значение |
|---|---|
| Файл | `D:\Tools\ghidra_12.1.3_PUBLIC\support\launch.properties` |
| Изменение | раскомментирована/задана строка `JAVA_HOME_OVERRIDE=D:\Tools\jdk-21` |
| Остальное содержимое файла | не менялось |
| Проверено | 2026-08-22 чтением файла; файл прочитан повторно в тот же день, строка та же (`OBSERVED`, confidence 0.99, oracle: `filesystem`) |
| Восстанавливается при переустановке Ghidra? | **НЕТ.** Файл входит в дистрибутив и будет заменён дефолтным |

Фактическое содержимое релевантного фрагмента:

```
# Force Ghidra's Java home instead of trying to figure it out automatically.
# If the provided path does not point to a supported Java home that Ghidra
# supports, this property is ignored.
# NOTE: Ghidra requires a JDK to launch.
JAVA_HOME_OVERRIDE=D:\Tools\jdk-21
```

#### Почему именно так, а не через системную переменную окружения

Состояние машины — примитивные чтения, каждое перезапущено повторно 2026-08-22 с тем же результатом (всё `OBSERVED`, confidence 0.99, oracle: `filesystem`; class P: читаются наличие переменной, порядок PATH и литеральные поля `application.properties`, без интерпретации):

* `JAVA_HOME` в системе **не задана** (`$env:JAVA_HOME` пуста);
* на PATH первым идёт `C:\Program Files (x86)\Common Files\Oracle\Java\javapath\java.exe` — это **Java 8 JRE 1.8.0_401**;
* `Ghidra/application.properties` содержит `application.java.min=21`.

Требование «именно **JDK**, а не JRE» — уже не строка из файла, а требование самой Ghidra, поэтому оно вынесено в отдельную запись (`HYPOTHESIS`, confidence 0.7, oracle: `external-doc`). Потолок «`external-doc` ≤ 0.7» из §6.2 п.1 к утверждению об инструменте формально не применяется (§1), но выше 0.7 мы его не поднимаем по собственной причине: запуск Ghidra на JRE 21 мы не делали, то есть падение без JDK не наблюдали. Косвенно требование подтверждает §7.1 (проверка `Test-Path javac.exe` в рецепте §8.1 существует именно из-за него).

То есть автоопределение JVM у Ghidra нашло бы Java 8 с PATH и упало бы. Дальше — почему выбран файл дистрибутива, а не переменная среды:

1. **Не трогать глобальное состояние машины.** Машина не выделена под этот проект. Установка системной `JAVA_HOME=D:\Tools\jdk-21` изменила бы поведение **всех** Java-приложений пользователя, включая те, которым нужна Java 8. Побочный эффект вне периметра задачи недопустим.
2. **Правка должна быть локальной и находимой.** Файл внутри установки Ghidra — самодокументируемое место: тот, кто разбирается с Ghidra, туда посмотрит. Системная переменная невидима и переживает удаление Ghidra, оставляя «висящую» настройку.
3. **Правка привязана к конкретной версии Ghidra.** Каталог установки содержит номер версии (`ghidra_12.1.3_PUBLIC`). Значит правка автоматически исчезает вместе с этой версией и не переносится молча на другую, для которой требования к JDK могут отличаться (§7.1).
4. **PATH ненадёжен по своей природе.** Порядок элементов PATH меняется от установки любого софта. Явный `JAVA_HOME_OVERRIDE` устраняет весь класс проблем «сегодня работало, завтра нет».
5. `JAVA_HOME_OVERRIDE` — **штатный, документированный** механизм самой Ghidra (комментарий в дистрибутиве, см. выше), а не хак.

#### Что обязан сделать любой, кто переустанавливает или обновляет Ghidra

1. Заново внести `JAVA_HOME_OVERRIDE` в `support/launch.properties` новой установки.
2. Перед этим — проверить `Ghidra/application.properties` новой версии на `application.java.min` / `max` / `compiler` и выполнить проверку запуском (§7.1). Не считать, что JDK 21 подойдёт и дальше.
3. Прогнать smoke-тест §8.3 и обновить `research/evidence/T-02/ghidra-smoke-test.md`.
4. Записать факт переустановки в `research/RESEARCH_LOG.md`, а смену версии JDK — ещё и в `research/decisions.md` (§7.3).

#### Побочный файл, который создаёт сама Ghidra

`%APPDATA%\ghidra\ghidra_12.1.3_PUBLIC\java_home.save` — кэш выбранной JVM, пишется Ghidra, **не нами**. Текущее содержимое: `D:\Tools\jdk-21` — файл прочитан дважды 2026-08-22, значение то же (`OBSERVED`, confidence 0.99, oracle: `filesystem`). Это не правка, а производный файл, но его надо знать: устаревший `java_home.save` от неудачного запуска способен сохранять сломанное состояние между попытками — см. `research/evidence/T-02/ghidra-jdk25-felix-failure.md`.

### 5.2 Явно НЕ сделанные изменения

Фиксируется, чтобы никто не искал того, чего нет:

## 6. Правила приобретения инструментов (§17.3)

### 6.1 Критерий допустимости

Инструмент допустим, если у него есть **все три** свойства:

1. **публичный исходный код**;
2. **воспроизводимый релиз** (именованный, версионированный, доступный повторно);
3. **проверяемая контрольная сумма** из независимого от самого файла источника (release notes, API, подписанный манифест).

Дополнительно:

* Сомнительные бинарники не скачиваются и не запускаются (AGENTS.md).
* Каждая внешняя зависимость получает запись в этом файле: имя, версия, URL, sha256, дата получения, зачем нужна и **что произойдёт без неё**.
* Закрытый бинарник без исходников — только с явным разрешением владельца проекта, и **никогда** против оригинальных контейнеров игры.
* `winget` на машине отсутствует (§9.2), поэтому канонический путь установки — **прямая загрузка + сверка sha256**, а не менеджер пакетов. Это не обходной путь, а штатная процедура здесь.

### 6.2 Разделение ролей: наши парсеры vs сторонние инструменты (C-12)

**Мы не переписываем экосистему Unreal IoStore самостоятельно** — это работа на месяцы с сомнительной отдачей (RISK-17). Но и не отдаём выводы на откуп чужому коду.

| | Наши собственные парсеры | Официальные UE-инструменты и проверенные open-source инструменты |
|---|---|---|
| Роль | **минимальные воспроизводимые метаданные**: заголовки контейнеров, PE, fingerprint, sig-scan, writer для Tier A | **независимый research oracle** для cross-validation наших выводов |
| Зачем нужны | fingerprint должен быть воспроизводим без внешних зависимостей и должен диффиться в git | второй независимый источник для §10.3 («два независимых метода») — резко ускоряет подтверждение форматов |
| Могут ли стать runtime-зависимостью framework | нет (это research-инструменты) | **категорически нет** |
| Область | ровно то, что нужно для наших артефактов, и ни байтом больше | что угодно, что помогает проверить наш вывод |

Правила использования сторонних инструментов как oracle:

1. Их результат несёт `oracle = external-doc` или `container-metadata` (§10.5) и **сам по себе** не даёт confidence выше **0.7** применительно к **этой** сборке — он свидетельствует о vanilla-UE-поведении, а не о MISERY.
2. **Расхождение** между нашим парсером и сторонним инструментом — это **находка, которую надо разобрать**, а не повод молча довериться одному из них. Записывается в `research/unknowns.md`.
3. **Ни один сторонний инструмент не становится runtime-зависимостью framework.** Его присутствие в toolchain не создаёт для будущего Runtime ни обязательств, ни архитектурных решений.
4. Применение любого инструмента к **оригинальным контейнерам игры** ограничено принятым **D-02**: расшифровка недопустима независимо от того, чьим кодом она выполняется. Наличие инструмента, умеющего это, не является разрешением.
5. Закрытый бинарник без исходников — только с явным разрешением владельца проекта, и никогда против оригинальных контейнеров.

Практическое применение на текущем окружении:

* `UnrealPak.exe` (§3) — законный oracle для Tier A: наш `pak_writer.py` пишет `.pak` v11, `UnrealPak` его читает. Расхождение → находка.
* `global.utoc` / `global.ucas` **не зашифрованы** (A-07, A-08), поэтому сторонние читалки контейнеров применимы к ним без нарушения D-02.
* `MISERY-Windows.utoc` / `.ucas` зашифрованы. **Исправлено 2026-08-23 (D-11):** запрещены извлечение
  ключа и расшифровка (в силе дословно); чтение метаданных без ключа — заголовков, счётчиков, флагов,
  индексов, доказанно-открытого payload — не запрещалось и выполняется штатно нашими же парсерами.
  Было ~~«любой инструмент против них — запрещён»~~. См. `docs/research-vs-product.md` §2, §7.

### 6.3 sha256 колёс из PyPI не зафиксированы — это признанный долг, а не исключение

Прямой ответ на вопрос «допустимо ли это по `plan.md` §17.3»: **нет, не допустимо; это записанный долг.**

`plan.md` §17.3 требует от каждого инструмента три свойства, третье из них — **проверяемая контрольная сумма**, и отдельно требует, чтобы каждая внешняя зависимость получила запись с sha256. Фактическое состояние:

| Артефакт | sha256 записан? |
|---|---|
| Ghidra 12.1.3, Temurin JDK 21 (архивы) | **да**, §4, сверены с независимым источником |
| pyghidra 3.1.0 (wheel из состава Ghidra) | **да**, §4; подлинность унаследована от проверенного архива |
| `jpype1 1.7.1`, `packaging 26.3` | **нет** — пробел существовал до 2026-08-22 |
| `jsonschema 4.26.0`, `pytest 9.1.1` | **нет** — тот же пробел, того же вида |
| восемь транзитивных колёс (`attrs`, `jsonschema-specifications`, `referencing`, `rpds-py`, `colorama`, `iniconfig`, `pluggy`, `Pygments`) | **нет** |

Почему это именно долг, а не приемлемое исключение:

* критерий выполним. PyPI публикует sha256 каждого файла, а pip умеет его требовать (`pip install --require-hashes`). То есть препятствия нет — мы просто не записали значения в момент установки;
* следовательно про эти одиннадцать колёс §6.1 п.3 сейчас **не выполнен**, и говорить «инструмент допустим» про них можно только с этой оговоркой;
* смягчающее обстоятельство ровно одно, и его не надо переоценивать: pip сверяет загрузку с хэшем из индекса PyPI, поэтому «случайно битый файл» отсекается. Что **не** отсекается — компрометация самого индекса и, что практичнее, «мы поставили не ту версию и не заметили»: без записанного хэша нельзя доказать, что на другой машине встал тот же файл;
* сборки из исходников не было ни для одного из них (§9.4), поэтому отсутствующий MSVC (§2.1) этот долг не усугубляет.

Долг зафиксирован в трёх местах и нигде не скрыт: строки `UNKNOWN` в Таблице B (§4), пункт 6 чеклиста (§15) и блок `WHEEL HASHES ARE NOT RECORDED` в `requirements.txt`. Закрытие — переход `requirements.txt` на `--require-hashes` с полным набором `--hash=sha256:...`, включая транзитивные. Значение `UNKNOWN` здесь стоит намеренно: догадка на его месте была бы хуже пробела (`plan.md` §10.1).

```
application.java.max=
application.java.compiler=21
application.python.supported=3.14, 3.13, 3.12, 3.11, 3.10, 3.9
application.version=12.1.3
```

* **Ключевой урок, за который уже заплачено временем: пустое `application.java.max` НЕ означает поддержку произвольно новых JDK.** Формально максимум не задан — фактически Ghidra 12.1.3 на Temurin JDK **25.0.1** падает в OSGi-подсистеме Apache Felix **до старта любой пользовательской логики**, и обойти это флагами не удаётся. Детали, стек и границы вывода — §12 и `research/evidence/T-02/ghidra-jdk25-felix-failure.md`.
* Следствие: одного чтения `application.properties` недостаточно **никогда**. Пункт 2 (запуск) не опционален.
* **При смене версии Ghidra эта проверка выполняется заново с нуля**, включая smoke-тест. Предыдущий результат не переносится.

### 7.2 Python

* **Python-окружение не обязано использовать системный Python 3.14.** Если зависимости лучше поддержаны другой версией (готовые колёса для 3.12/3.13 вместо сборки из исходников), допустимо поставить отдельный интерпретатор под research-venv.
* Критерий выбора — **«наименьшее число сборок из исходников и наименьшая хрупкость»**, а не «самая новая версия».
* На этой машине критерий особенно жёсткий: MSVC отсутствует (§2.1), поэтому **любая** сборка C-расширения из исходников гарантированно провалится. Версия Python выбирается так, чтобы для всех зависимостей существовали бинарные колёса.
* Текущее состояние: venv на системном **CPython 3.14.0**; это работает, потому что для `jpype1 1.7.1` колесо `cp314` существует. Обратите внимание, что 3.14 — верхняя граница `application.python.supported` Ghidra 12.1.3, то есть запаса вверх нет.
* Фактическая версия каждого окружения фиксируется здесь и в `requirements.txt`.

## 10. Дисковое ограничение — RISK-13

**Это ограничение toolchain, а не только строка в списке рисков.** Оно определяет, куда ставить инструменты и как запускать анализ.

Фактическое состояние. Метод — `Get-CimInstance Win32_LogicalDisk -Filter "DriveType=3"`, чтение полей `FreeSpace` и `Size`; метод перезапущен повторно 2026-08-22 и оба раза вернул те же поля (`OBSERVED`, confidence 0.99, oracle: `filesystem`):

| Диск | Свободно, первое чтение 2026-08-22 | Свободно, повторное чтение 2026-08-22 | Всего |
|---|---|---|---|
| **`C:`** | **3.06 ГБ** | **0.997 ГБ** (`1 070 608 384 B`) | 150.15 ГБ |
| `D:` | 98.64 ГБ | 98.65 ГБ | 781.25 ГБ |

> **Свободное место — величина летучая, и повторное чтение это показало наглядно: за один день `C:` потерял ~2 ГБ.** Поэтому запись выше устроена так: воспроизводимо здесь не *число*, а *метод*; число — это отсчёт на момент запуска, и confidence 0.99 относится к тому, что отсчёт снят и прочитан верно, а не к тому, что он будет тем же завтра.
>
> **Практическое следствие, а не формальность: `C:` уже на пороге остановки.** Правило §15 п.7 — «падение ниже ~1 ГБ → остановить анализ». Фактическое значение `0.997 ГБ` этот порог уже пересекло. Значит **полный автоанализ 134-МБ exe на текущем состоянии машины запускать нельзя**, и T-05 (§10.1 п.3) начинается не с измерения размера БД, а с освобождения места на `C:` либо с переноса кэшей Ghidra на `D:` (§10.1 п.6). Записи в `research/unknowns.md` / `research/decisions.md` — не в этом файле; здесь фиксируется только измерение.

**Проблема:** Ghidra кладёт свои каталоги настроек и кэшей **на `C:`**, независимо от того, где стоит сама Ghidra и где лежит проект:

| Каталог | Что там | Фактический размер 2026-08-22 |
|---|---|---|

### 12.2 Java 8 на PATH перехватывает автоопределение JVM

`C:\Program Files (x86)\Common Files\Oracle\Java\javapath\java.exe` = **1.8.0_401**, `JAVA_HOME` не задана. Любой Java-инструмент, полагающийся на PATH, получит Java 8. ### 12.3 `pyghidra 3.1.0` пинит `Jpype1==1.5.2`, у которого нет колеса cp314

Обход в §8.2. Первопричина двойная: отсутствие колеса `cp314` у jpype 1.5.2 **и** отсутствие MSVC для сборки из исходников (§2.1). Устранение любой из двух причин снимет проблему, но обход §8.2 проще и уже проверен.

### 12.4 MinGW-w64 GCC не заменяет MSVC

На машине два независимых GCC (§14.5). Ни один не годится ни для сборки UE C++ модуля на Windows (UE требует MSVC), ни для надёжной сборки CPython C-расширений под MSVC ABI. Считать «компилятор есть» — ошибка.

#### Почему этот блок генерируется, а не набирается руками

Потому что руками он устарел дважды за один день (2026-08-22), и второй раз — при полном внимании к нему. Это отказ механизма, а не дисциплины, и у отказа было две причины:

1. **Копий было две.** Те же числа стояли здесь и в шапке `.github/workflows/ci.yml`. Две рукописные копии одного изменчивого измерения расходятся всегда: обновляют ту, на которую смотрят.
2. **Ничто не падало, когда они переставали быть верными.** Комментарий и абзац не исполняются; они гниют молча, и по виду свежий абзац неотличим от протухшего.

Поэтому у изменчивых чисел теперь ровно один дом — область выше, ограниченная html-комментариями `BEGIN GENERATED kb-status` и `END GENERATED kb-status` (сами маркеры здесь намеренно приведены без обрамления `<!-- -->`: иначе этот абзац стал бы вторым «началом области» для генератора), — и наполняет её генератор:

| | команда | что делает |
|---|---|---|
| обновить | `python .github\scripts\kb_status.py --write` | запускает валидатор и набор тестов, перерисовывает область, ставит дату, HEAD и интерпретатор |
| проверить | `python .github\scripts\kb_status.py --check` | перемеряет, пересобирает область с **той же** датой и HEAD и печатает diff. Пустой diff — числа ещё верны; непустой — называет разошедшееся число. Выход 1 = блок устарел. Ничего не правит |

Измерение делает тот интерпретатор, которым запущен генератор, и он пишется в блок. Запускать его надо каноническим (§3.1) — иначе блок честно сообщит, что запускали не им.

CI запускает `--check` последним шагом и печатает вердикт в сводку прогона — **не** влияя на цвет задачи. Смысл этого шага не в свежести блока, а в том, что генератор исполняется при каждом прогоне и поэтому не может тихо сгнить в скрипт, который уже никто не может запустить. Вердикт `STALE` там — норма и не находка: CI прогоняется на коммите, который может быть новее того, на котором снят блок, и именно это датированный снимок и означает.

Остальные места про статус чисел не содержат вообще: `README.md` несёт **живой** значок CI и одну фразу о том, что означает его цвет; шапка `.github/workflows/ci.yml` — только объяснение и ссылку сюда; шаг «Generated status line» в CI печатает числа своего прогона в сводку. Если типизированное число статуса появилось во втором файле — это возврат дефекта, а не полезное дублирование.

**Чего этот механизм НЕ делает, чтобы его не переоценили:** он не гарантирует свежести. Ничто не заставляет запустить `--write` перед коммитом, и это сознательно — см. следующий подраздел. Он гарантирует три меньшие вещи: числа не набраны руками, они снабжены датой/HEAD/интерпретатором, и вопрос «устарело ли» отвечается одной командой вместо ручного сличения.

#### Как перепроверить этот блок — и почему это право, а не разрешение

Снимок не защищён ничем, кроме собственной даты, поэтому **любой читатель может и должен перезапустить его сам; свежий прогон всегда главнее написанного здесь.** Из корня репозитория:

```
D:\Tools\venv-research\Scripts\python.exe .github\scripts\kb_status.py --check
D:\Tools\venv-research\Scripts\python.exe .github\scripts\kb_status.py --write
```

Те же числа руками, без генератора, — двумя исходными командами (они же пункты 9 и 10 таблицы):

```
D:\Tools\venv-research\Scripts\python.exe tools\kb\validate.py
D:\Tools\venv-research\Scripts\python.exe -m pytest -q
```

Для машинного сравнения первая команда имеет форму `--json`, и генератор берёт числа **только** из неё: `schema_backend`, `summary.files`, `summary.records`, `summary.records_by_notation`, `summary.unparseable_records`, `summary.violations`, `summary.warnings`, `summary.by_rule`, `summary.exit_code`, плюс `errors` / `unparseable_count` / `warnings` по каждому файлу из `files[]`. Ничего сверх этого в блок не попадает, и ничего в нём не считается вручную.

Тот же набор чисел печатает и CI — шагом «Generated status line» в сводку прогона (`.github/workflows/ci.yml`). Та сводка устареть не может по построению: она не существует до прогона, который её породил. Здесь — сгенерированный снимок с датой, там — сгенерированная строка прогона; типизированного вручную статуса нет больше нигде, и заводить его снова не следует.

Почему **числа** этого блока не проверяются тестом, а **имена тестов** проверяются — см. следующий подраздел. И по той же причине `--check` **сознательно не встроен** ни в набор тестов, ни в CI: тест, требующий совпадения чисел в документе со свежим прогоном, краснел бы при каждом закрытом нарушении — то есть наказывал бы за прогресс, и его немедленно начали бы игнорировать. Числа поэтому защищены датой, генератором и командой перезапуска. А вот имя теста прогрессом не двигается: оно либо есть в наборе, либо его нет, и тут машинная проверка ничего не наказывает. Разделение именно по этому признаку: проверяем машиной то, что не шумит.

#### Что именно сгнило в прошлых версиях этого блока

Версия от 15:56 2026-08-22 к 16:44 была неверна почти в каждом числе: `records` 221 → 228, нечитаемых 9 → 7, прогон тестов «1 failed, 267 passed, 10 subtests» → «2 failed, 291 passed, 16 subtests». Совпало ровно одно число — `violations: 23`, — и именно это совпадение делало весь блок похожим на свежий.

Версия от 16:58 того же дня продержалась до вечера и сгнила так же: `records` 229 → больше двухсот сорока, `violations` 27 → меньше пятнадцати, нечитаемых 7 → 1, а разбивка по файлам приписывала `plan.md` 16 нарушений, когда их там осталось единицы. Второе гниение — то, ради которого блок стал генерируемым: одна и та же ошибка, повторённая при полном внимании к ней, означает, что виновата не невнимательность.

Хуже чисел был **состав провалов**. Прошлая версия называла единственным провалом `tests/test_discovery.py::TestEndToEnd::test_writes_to_a_different_drive_without_crashing` <!-- KB-NODE-GONE --> — тест, который к моменту чтения был удалён и заменён другим, то есть блок ссылался на имя, которого в репозитории уже нет. Прочесть это глазами невозможно: имя удалённого теста выглядит точно так же, как имя существующего.

Отсюда два вывода, встроенных в механику, а не в добрую волю:

1. **Имена тестов в документах проверяются машиной.** `tests/test_validator_live.py::DocumentedTestIdsExist::test_documented_node_ids_resolve` собирает все идентификаторы вида `tests/<модуль>.py::<Класс>::<тест>`, встречающиеся в тексте репозитория, и требует, чтобы каждый из них `pytest` действительно мог собрать.

   Для сознательной ссылки на удалённый тест — как в абзаце выше — есть маркер-оговорка `KB-NODE-GONE`, поставленный в той же строке. Он утверждает обратное (помеченный идентификатор **не** должен собираться) и тоже проверяется, так что бесплатного пропуска нет ни в одну сторону; `grep -rn KB-NODE-GONE` перечисляет все такие оговорки в репозитории. Оговорка действует построчно — поэтому объяснение маркера и живое имя теста не должны стоять в одной строке, иначе объяснение молча освободит от проверки то, что объясняет. Проверено на себе: первая редакция этого раздела так и сделала, и второй тест того же класса это поймал.
2. **Снимок пересдаётся не только когда сдвинулись числа, но и когда сменился СОСТАВ провалов.** Смена состава меняет смысл: «сломана фикстура» и «база знаний грязная» — разные новости, даже если суммарное число провалов одинаковое.

Для сравнения с историей: цифра «129 passed, 4 subtests passed», стоявшая здесь и в `requirements.txt`, относилась к двум тестовым модулям. Актуальное число — в сгенерированном блоке; оно давно больше втрое, то есть устарела та цифра не на опечатку. Сравнивать её с сегодняшним прогоном надо по блоку, а не по второй цифре, вписанной сюда рядом с первой: именно так пары устаревших чисел и заводятся.

### 15.2 Известное ограничение: JSON-нотация живым гейтом не покрыта

Валидатор различает четыре нотации записей. Три из них (`inline-annotation`, `table-row`, `log-entry`) в живом гейте `tests/test_validator_live.py` закрыты нижними порогами: если счётчик нотации обвалится, тест назовёт нотацию. Для четвёртой, `json`, порога нет — и это **объявленный пробел, а не ослабление**.

Причина: на 2026-08-22 валидатор даёт `json=0`. Четыре машиночитаемых артефакта под `research/builds/` проверяются по своим схемам, но ни один из них не несёт ни одной размеченной записи базы знаний. Ставить порог выше нуля не над чем — он падал бы по честной причине «фактов ещё нет».

Чего из-за этого не проверяет ни один прогон по реальному дереву:

- линтер записи для json-нотации — `lint_record` в `tools/kb/validate.py`, у которого параметр `notation` по умолчанию равен `json`; прозаические нотации идут через отдельный и заведомо более слабый `lint_markdown_record`;
- матрица `claim_type` → `oracle` из `plan.md` §10.5. Валидатор сам пишет в блоке DISCLOSURES, что применяет её **только** к json-записям: markdown-нотации поля `claim_type` не имеют вовсе;
- условные формы в `research/schema/kb-record.schema.json`;
- правило `build_key`.

Всё перечисленное сегодня проверяется исключительно синтетическими фикстурами в `tests/test_kb.py`. Аргумент самого живого гейта — «пустой обход и чистый обход по exit code неразличимы» — применим здесь в полном объёме: для json-нотации обход пуст.

**Чем пробел закрывается:** первой настоящей json-записью базы знаний. Чтобы это не осталось незамеченным, в гейте стоит не мёртвый «порог 0», а ратчет: `tests/test_validator_live.py::ValidatorLiveGate::test_json_notation_gap_is_still_declared` проходит, пока `json=0`, и краснеет в тот день, когда появится первая json-запись, — с инструкцией поставить настоящий порог и удалить этот раздел. Пробел может быть открыт; молча открытым он быть не может.

## 16. Чего в CI нет, и почему часть тестов там обязана скипаться

[![CI](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Merlion03/misery-modding-framework/actions/workflows/ci.yml)

Значок выше — единственный **живой** индикатор состояния в этом файле: он показывает цвет последнего прогона на `main` и устареть не может, потому что не является текстом. Всё остальное про прогоны в этом документе — сгенерированный снимок с датой (§15.1). Тот же значок стоит и в `README.md` — первым экраном, вместе с одной фразой о том, что означает его красный цвет: **красный гейт здесь означает, что наши собственные документы ещё не удовлетворяют нашим же правилам доказательности, а не что исследование сломано.** Числа в `README.md` при этом не дублируются сознательно: значок жив, а число пришлось бы обновлять руками — ровно тот дефект, из-за которого §15.1 стал генерируемым.

Репозиторий публичный, и в нём есть CI-workflow — `.github/workflows/ci.yml`. Значит появляется вторая среда исполнения — и она **беднее** описанной выше. Этот раздел существует ровно для того, чтобы жёлтый «skipped» в CI читался как «здесь этого нет», а не как «тесты сломали».

**Правило:** тест, которому нужен недоступный в CI компонент, обязан **скипаться с внятной причиной**, а не падать и не «проходить» на подделке. Провал в CI должен означать регрессию кода, и ничего больше.

| Компонент | В CI | Что из-за этого невозможно проверить в CI |
|---|---|---|
| **Установка игры** `D:\Games\Steam\steamapps\common\MISERY` | **нет** и не будет | всё, что читает реальные контейнеры, PE игры и inventory установки. Копировать установку в CI нельзя: это чужой платный контент, а репозиторий публичный (C-01, C-02, D-01, NOTICE.md). Тесты `pathguard` / discovery проверяемы на **синтетическом** дереве-заглушке, и именно так и должны быть написаны |
| **Ghidra 12.1.3 + Temurin JDK 21** | **нет** | smoke-тест §8.3, любой запуск `analyzeHeadless`, всё через PyGhidra (S-03..S-05, S-09, S-10). 863 МБ дистрибутива плюс JDK — это не «долгий шаг сборки», а внешний артефакт с обязательной сверкой sha256 (§6.1), и запускать его на каждый push смысла нет |
| **research venv** `D:\Tools\venv-research` | **нет** — venv живёт вне репозитория и вне CI | канонический интерпретатор §3.1 в CI недоступен буквально. CI создаёт **свой** venv по `requirements.txt`. Отсюда важное следствие: зелёный CI **не** отменяет требования §15 п.11 прогнать проверки локально каноническим интерпретатором — это две разные среды, и совпадение их состава гарантируется только `requirements.txt` |
| **PyGhidra и `jpype1`** | **не ставятся** | `pyghidra` берётся из wheel внутри установленной Ghidra (§4), которой в CI нет; `jpype1` без Ghidra бесполезен. В CI ставится только то, что нужно валидатору и тестам: `jsonschema`, `pytest`, `packaging` |
| **Unreal Engine 5.4.4 / `UnrealPak.exe`** | **нет** (37 ГБ) | cook/stage/pack, cross-validation Tier A против `UnrealPak` (§6.2) |
| **MSVC** | нет (и локально тоже нет, §2.1) | ничего дополнительно: этот пробел в CI и на машине одинаков |
| **Диски `C:` / `D:` с их занятостью** | не применимо | RISK-13 (§10) — свойство **этой** машины. Проверка §15 п.7 в CI бессмысленна и должна скипаться, а не выдумывать порог |
| `tools/kb/validate.py`, `tests/`, чистая `pathguard`-логика на синтетическом дереве | **да** | это и есть то, что CI действительно защищает |

Из таблицы следуют два вывода, которые стоит держать в голове при чтении CI-логов:

1. **Пустой набор скипов в CI — подозрителен.** Если тест, требующий Ghidra или установки игры, в CI «прошёл», значит он проверил заглушку и молчаливо ничего не доказал. Это тот же класс дефекта, что деградация валидатора до встроенного бэкенда (§3.1).
2. **CI не является oracle для утверждений об этой сборке игры.** Ни одно утверждение с `oracle = filesystem` про установку MISERY в CI не воспроизводимо в принципе, потому что установки там нет. CI подтверждает код, а не факты о сборке.
